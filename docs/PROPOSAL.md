# 연구 기획서

**포스트퀀텀 하이브리드 키 교환의 다운그레이드 저항성 — 증명된 설계와 실제 구현 사이의 간극**

- 작성일: 2026-09-22
- 관심 분야: 정보보안 / 암호 프로토콜·포스트퀀텀 전환·구현 보안

---

## 1. 연구 문제

> 하이브리드 키 교환의 다운그레이드 저항성은 프로토콜 설계 수준에서 이미 형식적으로 증명되어 있는데, 실제 배포된 구현체들도 그 증명대로 동작하는가.

포스트퀀텀 마이그레이션 중인 조직 대부분은 "표준 하이브리드 구성을 따랐으니 다운그레이드에 안전하다"고 가정한다. 이 연구는 그 가정이 구현 단계에서 깨질 수 있는지를 직접 검증한다.

## 2. 연구 배경

매일 NVD 신규 등록 CVE를 자동 수집하는 개인 사이트([Today-CVE-information](https://github.com/whiteclover0542/Today-CVE-information), 2026-08-22부터 운영)를 지켜보던 중, 실제 기록(2026-08-23~09-22)에서 프로토콜 협상·핸드셰이크 로직 결함이 반복적으로 보고되는 패턴을 확인했다.

| CVE | 날짜 | 내용 |
| --- | --- | --- |
| [CVE-2026-91949](https://nvd.nist.gov/vuln/detail/CVE-2026-91949) | 2026-09-16 | FreeRDP 서버의 프로토콜 협상 우회 |
| [CVE-2026-20249](https://nvd.nist.gov/vuln/detail/CVE-2026-20249) | 2026-09-17 | Cisco ASA/FTD IKEv2 인증 단계 로직 오류 |
| [CVE-2026-90439](https://nvd.nist.gov/vuln/detail/CVE-2026-90439) | 2026-09-16 | NGINX `ngx_http_v3_module`(HTTP/3)의 힙 버퍼 오버플로우 |

세 CVE의 공통점은 결함의 **종류**가 아니라 결함이 발생하는 **위치**다. FreeRDP는 협상 절차 자체를 우회하고, Cisco IKEv2는 인증 단계의 로직이 틀렸고, NGINX는 HTTP/3 핸드셰이크 처리 중 메모리 오류가 났다 — 형태는 다르지만 셋 다 "서로 무엇을 쓸지 정하는 협상·핸드셰이크 단계"에서 문제가 생겼고, 그 문제가 겉으로는 정상 동작처럼 보인다는 점이 반복됐다.

이 흐름을 좇던 중, TLS 핸드셰이크 협상을 다루는 OpenSSL 3.5 라인에서 포스트퀀텀 하이브리드 그룹 협상이 감사 도구에 걸리지 않는 방식으로 고전 방식으로 다운그레이드되는 결함([CVE-2026-2673](https://nvd.nist.gov/vuln/detail/CVE-2026-2673), 2026-03-13 공개, OpenSSL 3.5/3.6 영향)이 이미 보고됐던 것을 확인했다. 여기서 "협상 로직의 결함이 하이브리드 PQ 다운그레이드로 이어지는 것이 특정 라이브러리의 우연한 버그인지, 아니면 여러 구현체에 걸친 일반적 패턴인지"라는 질문으로 주제를 좁혔다.

## 3. 연구의 필요성과 의의

1. **읽는 사람이 자기 시스템을 다시 보게 되는가.** 포스트퀀텀 마이그레이션 중인 조직 대부분이 표준 하이브리드 구성만으로 다운그레이드에 안전하다고 가정한다. 그 가정이 구현 단계에서 깨질 수 있음을 보여준다.
2. **반직관적인가.** 하이브리드 컴바이너의 다운그레이드 저항성은 이미 형식적으로 증명된 안전한 설계다(Bhargavan et al.의 정의, 2026년 9월 "Transcript-Bound Combiners for Downgrade-Resilient Hybrid PQ Key Establishment" 등). 그럼에도 실제 OpenSSL 구현에서 표준 TLS 감사 도구로는 감지되지 않는 방식으로 고전 전용 그룹에 조용히 폴백하는 결함(CVE-2026-2673)이 실제로 발생했다. "증명된 안전함"과 "실제 배포된 안전함" 사이의 간극이 핵심이다.
3. **실제로 수행할 수 있는가.** 대용량 데이터나 GPU 학습이 필요 없고, 로컬 환경에 OpenSSL(oqs-provider), BoringSSL, OpenSSH의 하이브리드 KEM 구현을 직접 설치해 통제된 결함 주입·패킷 조작으로 다운그레이드·컴바이너 바인딩 위반을 재현·측정할 수 있다.

## 4. 실험 아키텍처

### 4.1 시스템 구성도

```
        (하이브리드 그룹 목록 포함 ClientHello)
[Client] ───────────────────────────────▶ [Fault Injector]
                                                │
                                    그룹 목록 절단 / 순서 조작 /
                                    트랜스크립트 바인딩 변조
                                                │
                                                ▼
                                            [Server]
[Client] ◀─────────────────────────────── (ServerHello: 선택된 그룹)
                                                │
                                                ▼
                                   [감사 로그 / 패킷 캡처 수집]
                                   (SSLKEYLOGFILE, s_server -state,
                                    sshd -vvv, Wireshark 덤프)
```

Fault Injector는 클라이언트·서버 사이에서 TLS 레코드 계층을 가로채는 중간자 형태의 테스트 하네스로, 그룹 협상 필드를 통제된 방식으로 조작한 뒤 결과를 로그·패킷 캡처로 수집한다.

### 4.2 대상 구현체 (테스트베드)

| 구현체 | 하이브리드 메커니즘(예) | 비고 |
| --- | --- | --- |
| OpenSSL + oqs-provider | X25519MLKEM768 등 | CVE-2026-2673 보고 대상 라인 |
| BoringSSL | X25519Kyber768 (자체 그룹 ID) | Google 관리, 별도 협상 코드 경로 |
| OpenSSH | sntrup761x25519-sha512 등 | TLS가 아닌 SSH 프로토콜 스택 — 협상 로직 비교군 |

세 구현체는 서로 독립적인 코드베이스이므로, 동일한 결함이 여러 구현체에서 재현되는지를 통해 "특정 라이브러리의 우연한 버그" 대 "일반적 패턴" 여부를 구분할 수 있다.

### 4.3 결함 주입 방법

- **그룹 목록 조작**: ClientHello의 `supported_groups`/KEX 알고리즘 목록에서 하이브리드 그룹을 제거하거나 순서를 바꿔, 서버가 고전 전용 그룹으로 응답하도록 유도한다.
- **컴바이너 바인딩 위반 시도**: 하이브리드 키 교환의 두 성분(고전/PQ) 중 하나만 실제 값으로 채우고 나머지는 조작된 값으로 대체해, 트랜스크립트 바인딩 검증이 이를 걸러내는지 확인한다.
- **도구**: Python 기반 스크립트(scapy 또는 OpenSSL `s_client`/`s_server`의 저수준 후킹), 필요 시 mitmproxy류 프록시를 TLS 레코드 조작용으로 확장해 사용한다.

### 4.4 관측 지표

| 지표 | 설명 |
| --- | --- |
| 협상 결과 그룹 | 핸드셰이크가 최종적으로 선택한 key_share 그룹이 하이브리드인지 고전 전용인지 |
| 감사 도구 탐지 여부 | 표준 로깅(SSLKEYLOGFILE, `-state`, `-vvv`)·Wireshark 캡처에 다운그레이드 사실이 드러나는지 |
| 핸드셰이크 성공/실패 | 조작된 협상이 연결 거부로 이어지는지, 조용히 성공하는지 |

## 5. 연구 수행 절차

1. 하이브리드 KEM을 구현한 대상 오픈소스(OpenSSL+oqs-provider, BoringSSL, OpenSSH)를 로컬 환경에 구축한다.
2. 위 아키텍처에 따라 결함 주입·패킷 조작 실험을 설계하고, 구현체 × 결함 유형 × 반복 조합으로 최소 10회 이상 반복 실행한다.
3. 관측 지표(협상 결과, 감사 도구 탐지 여부, 핸드셰이크 성공 여부)를 원자료로 기록한다.
4. 구현체별 결과를 비교해, 협상 로직 결함이 특정 라이브러리의 우연한 버그인지 여러 구현체에 걸친 일반적 패턴인지 판단한다.

## 6. 예상 산출물

- 구현체별 다운그레이드/컴바이너 바인딩 위반 재현 여부와 감사 도구 탐지 여부를 정리한 비교표
- 실험에 사용한 결함 주입 스크립트와 원자료(로그, 패킷 캡처)
- 위 결과를 바탕으로 한 결론(패턴 여부에 대한 판단)과 한계 서술
