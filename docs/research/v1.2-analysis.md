## 4. 판정

[확실] `analyze --v12`의 `cve_verdict` 계산은 `(True, [])`, 즉 `CVE-2026-2673 verdict: reproduced`였다. 설계 §8 문구를 그대로 사용한다:

> [확실] 이 고정된 테스트베드에서 CVE-2026-2673 발현 조건과 수정 대조를 재현했다.

근거 수치(§3 표):

- 3.5.5 S3(`DEFAULT`): 10/10 반복에서 PCAP HRR 없음(HRR (PCAP)=0/10), 최종 협상 그룹 전부 `X25519`(classical=10/10) — HRR 없이 classical handshake 완료.
- 3.5.6 S3(`DEFAULT`): 10/10 반복에서 PCAP HRR 있음(HRR (PCAP)=10/10), 최종 협상 그룹 전부 `X25519MLKEM768`(hybrid=10/10) — HRR을 보낸 뒤 hybrid handshake 완료.
- S1·S2도 예상대로 각 20건(3.5.5+3.5.6 각 10)이 나왔다(§5).

[확실] `precondition-failed 실행은 결론 표본에서 제외된다`는 규칙의 해석: `cve_verdict`는 필수 조합(3.5.5/3.5.6 × S1/S2/S3)마다 정확히 10회의 유효 반복을 요구한다(`comparison_v12`가 반복 번호 집합 `{1..10}`과 `precondition`/`artifacts_complete`/`provenance_complete`/`success`가 모두 `n`과 같은지 확인). 따라서 하나라도 전제 검증(`client_precondition_verified`)에 실패하면 유효 표본이 10 미만이 되고, 판정 함수는 표본을 몰래 줄여서 나머지로 판정하지 않고 그 조합을 `failures`에 추가해 전체 판정을 `not reproduced`로 되돌린다 — 즉 전제 실패는 표본을 축소하는 대신 판정 자체를 막는다. 이번 60회 실행은 모든 조합에서 `precondition/n = 10/10`이었으므로 이 차단 조건이 실제로 발동하지는 않았지만, 규칙 자체는 위와 같이 설계되어 있다.

## 5. S1/S2 해석

[확실] 설계 §8에 따라: S1(`X25519MLKEM768:X25519`, 명시적 single tuple)에서 HRR이 없고 classical `X25519`가 선택되는 것은 명시적 single tuple의 문서상 동작이며, CVE 발현 또는 취약점 증거로 쓰지 않는다. §3 표에서 3.5.5·3.5.6 S1 모두 HRR (PCAP)=0/10, classical=10/10으로 이 문서상 동작과 일치했다.

[확실] S2(`X25519MLKEM768/X25519`, 명시적 tuple 경계)는 tuple 경계에서 HRR이 나오는 대조군이며, CVE 경로가 아니다. §3 표에서 3.5.5·3.5.6 S2 모두 HRR (PCAP)=10/10, hybrid=10/10으로 일관됐다.

## 6. 감사 가시성

[확실] §3 표의 `explicit warning`, `single-output mismatch` 열은 6개 조합 전부 `0`이었다. 즉 v1.2의 60건 중 하드코딩되지 않은 실측 지표(`tools/faultinject/audit.py`)로도 경고 서명이 명시적으로 검출된 레코드는 없었고(`explicit_warning=True` 0건), 단일 출력 안에서 광고 그룹과 협상 결과가 동시에 식별되는 사례도 없었다(`mismatch_in_single_output=True` 0건). 이는 §2에서 인용한 `openssl_server-setting_r01_3.5.6-S3.json`의 `audit.paths` 값(`client_log`/`server_log`/`tshark_summary` 모두 `mismatch_in_single_output="unsupported"`, `s_client -brief`/`keylog`는 `"not_collected"`)과 일치한다 — OpenSSL `-msg` 로그는 협상 결과 줄만 있고 광고 그룹 줄이 없어 "확인 불가(unsupported)"로 남는다는 v1.1 재계산(§ 아래 인용)의 도구 한계가 v1.2에서도 동일하게 재현된 것이다.

[확실] 각 JSON 레코드에는 v1.0/v1.1부터 남아 있는 레거시 필드 `metrics.downgrade_visible`도 있으며, S1·S3 레코드에서는 `True`(60건 중 40건, S1 20건+S3 20건), S2에서는 `False`다. 이 필드는 감사 가시성 측정값이 아니라 v1.0/v1.1 하네스의 하드코딩된 휴리스틱("하이브리드를 광고했는데 협상 결과가 classical")일 뿐이며, 어떤 감사 도구가 실제로 이를 탐지했는지는 말하지 않는다. v1.2가 실측하는 감사 가시성은 `record.audit`(§2.4, `tools/faultinject/audit.py`)에 있고, 이 문서 §6이 보고하는 `explicit_warning`·`mismatch_in_single_output`이 그것이다. `downgrade_visible=True`를 감사 경로가 다운그레이드를 감지했다는 근거로 읽어서는 안 된다.

[확실] `docs/research/v1.2-audit-v1.1-recompute.md` 요약: v1.1 원시 90건(재실행하지 않고 기존 로그·PCAP만으로 재계산, 도구 커밋 `f99f79b1b36feac06069035c3e1dc44dd55a98d5`)에서 `explicit_warning`은 90건 전부 `False`(unknown 0건)였고, `mismatch_in_single_output`은 openssh 30건(base/onpath-strip/ssh-order)만 `True`이고 나머지 60건(boringssl 30건, openssl 30건)은 `"unsupported"`(unknown 0건)였다. `s_client -brief`와 `keylog` 두 경로는 v1.1에서 수집되지 않아 `not_collected`로 고정됐다. 이 재계산 동안 `docs/research/baselines/raw/v1.1/` 원본은 읽기만 했고 수정하지 않았다(`git status --short docs/research/baselines/raw/v1.1` 출력 없음으로 확인, 본 문서 §9와 동일한 확인을 v1.2 실행 전후로도 재확인했다).

[확실] S4(`-groups` 인자 자체를 생략)는 두 버전 모두 20/20에서 HRR 후 hybrid로 수렴했다. 이를 "클라이언트 선호 순서" 탓으로 설명하는 것은 근거와 맞지 않는다 — 클라이언트는 `X25519:X25519MLKEM768`로 `X25519`를 먼저 광고하므로(§2), client preference 아래 단일 tuple이라면 HRR 없이 `X25519`가 즉시 수락되어야 한다(§5의 S1과 동일 논리). 실제 원인은 `docs/research/v1.2-normative-analysis.md` §3에 인용된 `TLS_DEFAULT_GROUP_LIST`(`ssl/t1_lib.c:204-205`, "/"로 구분된 4개 tuple)의 tuple 경계다: `-groups`를 생략하면 OpenSSL은 이 컴파일된 기본 목록을 CLI 문자열 파서를 거치지 않고 직접 사용하므로 tuple 구조가 보존되고, X25519MLKEM768과 X25519가 서로 다른 tuple에 속해 S2와 같은 tuple 경계 HRR이 3.5.5에서도 정상적으로 발생한다. 이는 S3(`DEFAULT`라는 키워드 문자열을 `-groups`로 명시해 별도의 확장 경로를 통과시키는 경우)의 3.5.5에서만 tuple 구조가 사라지는 것과 대비된다 — 즉 결함은 기본 그룹 목록 자체가 아니라 `DEFAULT` 키워드 확장 경로에 국한된다. 이 대비가 CVE 메커니즘을 특정하는 데 도움이 되지만, S4는 여전히 결론 표본(S1–S3, §1/§4)에 포함하지 않으며 판정 문구에도 쓰지 않는다.

## 9. BoringSSL

[확실] A-0 조사(`docs/research/v1.2-a0-environment.md` §5) 결론: BoringSSL은 `SSL_OP_CIPHER_SERVER_PREFERENCE` + 순서가 있는 평평한(flat) 그룹 ID 목록(`SSL_CTX_set1_group_ids`/`SSL_CTX_set1_groups_list`)만 제공하며, OpenSSL의 콜론(`:`)/슬래시(`/`) tuple 구문이나 `DEFAULT` 키워드에 대응하는 설정 문법 자체가 없다(`bssl server --help`에도 해당 CLI 옵션 없음, 라이브러리 API로만 서버 preference를 켤 수 있음). 따라서 "구조화된 tuple을 파싱하다가 평평한 목록으로 잃어버리는" CVE-2026-2673과 동일한 버그 클래스가 BoringSSL API 형태에서는 애초에 발생할 수 없다. 설계 §4.2에 따라 인위적 동등 조건을 만들지 않았고, 결과 문구는 "OpenSSL `DEFAULT` CVE 비교에 대한 설정 수단을 확인하지 못함"으로 제한했다 — BoringSSL은 v1.2 핵심 CVE 표본(§1~§4)에 포함되지 않는다.

[확실] A-0 대장에 추가로 기록된 사실: v1.1 BoringSSL `silent-downgrade` 조건의 ClientHello `key_share`는 실제로는 `[0x001D, 0x6399]`(X25519, X25519MLKEM768) 두 개였다(2026-09-28 PCAP 원시 바이트 재해석, `pcap_hello.summarize_hellos()`로 재확인 가능). 즉 v1.1 BoringSSL 행은 "고전 키만 제시"가 아니라, 하이브리드 key share도 함께 받은 상태에서 서버가 `X25519`를 선택한 경우로 재해석해야 한다.

## 10. 한계

[확실] `s_client -brief`와 keylog 감사 경로는 이번 v1.2 60회 실행에서도 수집하지 않았다(v1.2 클라이언트는 `-state -msg`로 실행되어 `-brief` 출력을 캡처하지 않으며, NSS 키 로그도 남기지 않았다). 이는 §2의 인용 레코드에서 보듯 `audit.paths["s_client -brief"]`/`["keylog"]`가 `mismatch_in_single_output="not_collected"`로 고정되는 설계상 결정이며, 우연한 누락이 아니다.

[확실] `tools/faultinject/pcap_hello.py` 기반 파서는 TCP로 세그먼트된(여러 TCP segment에 걸쳐 재조립되는) TLS Hello를 처리하지 않는다. 본 60회는 loopback에서 소규모 핸드셰이크 메시지만 오갔으므로 세그먼트 분할이 관측되지 않았지만, 더 큰 인증서 체인 등으로 메시지가 커지는 환경에서는 이 파서 제약이 `hrr_pcap_present`/`final_negotiated_group` 판정에 영향을 줄 수 있다.

[확실] 서버는 두 버전 모두 client preference 정책(`-serverpref` 미지정)으로 고정했다. server preference를 켠 환경에서의 동작은 시험하지 않았다.

[확실] 모든 실행은 loopback(127.0.0.1)에서만 수행했으며, 경로상 네트워크 지연·MITM·실배포 조건은 포함하지 않는다.

[확실] OpenSSL 버전은 3.5.5(재사용 native-only 설치)와 3.5.6(수정 대조군 빌드) 두 개로 고정했다. 다른 마이너/패치 버전이나 배포판 패키지의 동작은 일반화하지 않는다.

[확실] 각 필수 version×setting 조합의 반복 횟수는 10회로 고정했다(§5 설계). 더 많은 반복에서 다른 분포가 나올 가능성은 이 표본만으로 배제할 수 없다.
