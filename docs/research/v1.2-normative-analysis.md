## 2. RFC 8446 원문 (rfc-editor.org .txt, SHA-256 `47871bc8820a2c3b6ea89f061055577058862cf543686b82d10131239702b3bd`, 접근일 2026-09-28)

이 SHA-256은 `urllib.request.urlopen("https://www.rfc-editor.org/rfc/rfc8446.txt").read()`로 받은 바이트열 그대로에 대한 해시다(2026-09-28 실행).

### §4.1.1 Cryptographic Negotiation

> "If the server selects an (EC)DHE group and the client did not offer a compatible "key_share" extension in the initial ClientHello, the server MUST respond with a HelloRetryRequest (Section 4.1.4) message." (§4.1.1)

> "If the server does not select a PSK, then the first three of these options are entirely orthogonal: the server independently selects a cipher suite, an (EC)DHE group and key share for key establishment, and a signature algorithm/certificate pair to authenticate itself to the client." (§4.1.1)

### §4.1.4 Hello Retry Request

> "The server will send this message in response to a ClientHello message if it is able to find an acceptable set of parameters but the ClientHello does not contain sufficient information to proceed with the handshake." (§4.1.4)

### §4.2.7 Supported Groups

> "If the server has a group it prefers to the ones in the "key_share" extension but is still willing to accept the ClientHello, it SHOULD send "supported_groups" to update the client's view of its preferences; this extension SHOULD contain all groups the server supports, regardless of whether they are currently supported by the client." (§4.2.7)

### §4.2.8 Key Share

> "Clients MAY send an empty client_shares vector in order to request group selection from the server, at the cost of an additional round trip (see Section 4.1.4)." (§4.2.8)

> "selected_group: The mutually supported group the server intends to negotiate and is requesting a retried ClientHello/KeyShare for." (§4.2.8, `KeyShareHelloRetryRequest` 필드 설명)

## 3. OpenSSL 3.5 문서·소스 원문

출처: WSL(`/root/pq-hybrid-phase2/openssl`), 2026-09-28 실행. `doc/man3/SSL_CTX_set1_curves.pod`와 `ssl/t1_lib.c`는 v1.2 A-0/실험에 사용한 것과 동일한 3.5.5 소스 트리(§v1.2-a0-environment.md §3.7.1, commit `67b5686b4419b4cb8caa502711c41815f5279751`)다.

### 의사코드 (`doc/man3/SSL_CTX_set1_curves.pod:153-167`)

> ```
>  FOR each group tuple
>      IF client preference (= default)
>          FOR each client key-share group
>              IF current key-share group is also part of current group tuple: SH, return success
>          FOR each client supported groups
>              IF current supported group is also part of current group tuple: HRR, return success
>      ELSE (= server preference = with SSL_OP_CIPHER_SERVER_PREFERENCE option set)
>          FOR each group in current tuple
>              IF current group is also part of client key-share groups: SH, return success
>          FOR each group in current tuple
>              IF current group is also part of client supported groups: HRR, return success
>  return failure
> ```

`doc/man3/SSL_CTX_set1_curves.pod:169-171`:

> "Hence, if a client supports a group in a server group tuple, but does not send a key share for this group, a Hello Retry Request (HRR) is triggered, asking the client to send a new Hello message with a more preferred keyshare."

### tuple 경계 예시 (`doc/man3/SSL_CTX_set1_curves.pod:274-287`)

> "As a separate example, consider a server I<list> "A:B/C:D/E:F". Listed in order of highest preference to least, 3 group tuples are created: "A:B", "C:D", and "E:F"."

> "- "B:*C": Both prefer "B" from the first group tuple "A:B", so an HRR is triggered for "B"." (`:283-284`)

### 기본 tuple 목록 (`ssl/t1_lib.c:204-205`)

> ```c
> #define TLS_DEFAULT_GROUP_LIST \
>     "?*X25519MLKEM768 / ?*X25519:?secp256r1 / ?X448:?secp384r1:?secp521r1 / ?ffdhe2048:?ffdhe3072"
> ```

## 4. 해석 (원문과 분리, 태그 필수)

### Q1. 클라이언트가 이미 수락 가능한 key_share를 보냈을 때 서버는 더 선호하는 그룹을 위해 HRR을 보낼 의무가 있는가?

[확실] RFC 8446 §4.1.1의 MUST 문장은 조건부다 — "the client did not offer a compatible "key_share" extension"일 때에만 HRR이 MUST다. 클라이언트가 이미 서버가 수락하기로 한 그룹의 key_share를 보냈다면 이 MUST의 전제 조건이 성립하지 않는다.

[확실] §4.2.7은 정확히 이 시나리오("서버가 key_share에 없는, 더 선호하는 그룹을 갖고 있지만 여전히 ClientHello를 수락할 의향이 있는" 경우)를 명시적으로 다루며, 처방은 SHOULD 수준의 `supported_groups` 확장(클라이언트에게 향후 연결을 위한 선호도를 알려주는 정보성 힌트)뿐이다. MUST 수준의 HRR 의무는 이 경우에 대해 별도로 규정되어 있지 않다.

[확실] 따라서 Q1의 RFC 8446 문언상 답은 "의무 없음"이다 — 클라이언트가 이미 수락 가능한 key_share를 보냈다면, 더 선호하는 그룹을 위한 HRR은 RFC 8446이 강제하지 않는다. 다만 [불확실] RFC 8446이 이 경우 HRR을 "금지"하는 것도 아니다 — §4.1.4는 HRR을 "acceptable set of parameters를 찾았지만 ClientHello가 진행에 충분한 정보를 담지 않은 경우"로 기술할 뿐, 그 반대 경우(정보가 충분한데도 서버가 HRR을 선택하는 경우)를 금지하는 문장은 찾지 못했다. 즉 RFC 8446 텍스트만으로는 "더 선호하는 그룹을 위한 선택적 HRR"이 허용되는지 금지되는지까지는 결정되지 않는다 — 이 지점은 [불확실]로 남긴다.

### Q2. RFC 8446은 그룹 선택 기준을 서버 정책에 맡기는가?

[확실] §4.1.1은 "the server independently selects a cipher suite, an (EC)DHE group and key share for key establishment"라고만 말하고, 어떤 그룹을 "가장 선호되는" 것으로 취급해야 하는지, tuple을 어떻게 구성해야 하는지 등 선택 알고리즘 자체는 규정하지 않는다.

[추정] 이로부터 그룹 선택의 구체적 기준(어떤 그룹을 우선할지, HRR을 언제 선택적으로 사용할지)은 RFC 8446 문언에는 없고 각 구현체의 정책(설정 문법, 기본값)에 맡겨져 있다고 해석하는 것이 합리적이다 — "정책"이라는 단어 자체는 RFC 8446에 등장하지 않으므로 이 등치는 직접 인용이 아니라 추정이다.

### Q3. S1/S2/S3의 RFC 8446·OpenSSL 문서 정책상 위치

| 설정 | 서버 group-list | 관측(v1.2, §3/§5 v1.2-analysis.md) | RFC 8446 허용 여부 | OpenSSL 문서 정책과의 일치 여부 |
| --- | --- | --- | --- | --- |
| S1 | `X25519MLKEM768:X25519`(단일 tuple) | 3.5.5·3.5.6 모두 HRR 없음(0/10), classical 10/10 | [확실] 예 — 클라이언트가 이미 수락 가능한 key_share(X25519)를 보냈으므로 §4.1.1의 MUST-HRR 전제가 성립하지 않는다(Q1과 동일 논리) | [확실] 일치 — 의사코드의 "client key-share group이 현재 tuple에 속하면 SH, return success" 단계(pod:156)와 정확히 대응한다. 단일 tuple 안에 X25519MLKEM768과 X25519가 함께 있으므로 client key-share 루프에서 X25519가 즉시 매치되어 HRR 이전에 성공 반환된다 |
| S2 | `X25519MLKEM768/X25519`(두 tuple, tuple 경계) | 3.5.5·3.5.6 모두 HRR 있음(10/10), hybrid 10/10 | [확실] 예 — 서버가 선택하는 그룹(X25519MLKEM768)에 대해 클라이언트가 key_share를 보내지 않았으므로 §4.1.1의 MUST-HRR 전제가 성립하고 HRR이 요구된다 | [확실] 일치 — 의사코드의 tuple 경계 HRR 단계(pod:157-158) 및 문서의 "B:*C" 예시(pod:283-284, "Both prefer 'B' from the first group tuple... an HRR is triggered")와 동일한 구조 |

### CVE-2026-2673의 위치

[확실] 권고문에서 직접 확인한 사실(`docs/research/cve-2026-2673.md` §"권고문에서 직접 확인한 사실", 19-23행): "OpenSSL TLS 1.3 서버가 key exchange group 설정에 `DEFAULT` 키워드를 포함하면, 클라이언트와 서버가 더 선호된 그룹을 모두 지원하더라도 클라이언트의 초기 predicted key share에 그 그룹이 없을 때 덜 선호된 그룹을 선택할 수 있다"이며, "`DEFAULT` 목록을 서버 설정에 삽입하는 과정에서 group tuple 구조가 사라지고 모든 서버 지원 그룹이 하나의 sufficiently secure tuple로 취급된다"는 것이 결함 메커니즘이다.

[확실] v1.2 판정(`docs/research/v1.2-analysis.md` §4): `analyze --v12`는 `CVE-2026-2673 verdict: reproduced`를 출력했다. 근거(§3 표): 3.5.5 S3(`DEFAULT`)는 10/10 반복에서 PCAP HRR 없이(HRR (PCAP)=0/10) classical(X25519) 협상으로 완료(classical=10/10)됐고, 3.5.6 S3는 10/10 반복에서 PCAP HRR이 있었고(HRR (PCAP)=10/10) hybrid(X25519MLKEM768) 협상으로 완료(hybrid=10/10)됐다.

[확실] 위 Q3 표와 종합하면, CVE-2026-2673은 **RFC 8446 위반이 아니라 OpenSSL이 자신이 문서화한 tuple 기반 group-selection 정책(§3의 의사코드, `TLS_DEFAULT_GROUP_LIST`의 tuple 구문)을 `DEFAULT` 확장 과정에서 스스로 지키지 못한 구현 결함**으로 위치 짓는 것이 근거와 일치한다. RFC 8446 문언에는 이 사례가 위반하는 MUST 문장이 확인되지 않았다(Q1·Q3 S3-3.5.5 행). CWE 분류(CWE-757, Selection of Less-Secure Algorithm During Negotiation)도 프로토콜 표준 위반이 아니라 알고리즘 선택 로직의 결함으로 이 사례를 규정하고 있으며, 이는 위 해석과 부합한다.

### Step 3 세부 기록 (2026-09-28, WebFetch)

[확실] `draft-ietf-tls-hybrid-design`은 datatracker 페이지 확인 결과 초안 상태가 아니라 **RFC 9954**(Informational, 2026-07 발행)로 이미 발행되어 있었다. 이 페이지에서 "키 공유 누락 시 HRR"과 관련된 문장은 검색되지 않았다 — 해당 문장 없음.

[확실] `draft-ietf-tls-ecdhe-mlkem`도 초안이 아니라 **RFC 10024**(Proposed Standard, 2026-08 발행)로 이미 발행되어 있었다.

[불확실] 두 문서 모두 초안 단계를 지나 RFC로 승격된 시점이 본 연구팀의 사전 인지(모델 지식 컷오프 2026-01) 이후이므로, 이 사실은 2026-09-28 WebFetch 결과에만 의존한다. 원문 전체를 직접 열람해 재확인하지 않았으므로, RFC 번호·발행월 표기에 오류가 있을 가능성을 배제할 수 없다.
