## Interpretation constrained to the testbed

### TLS key-share-order observation (condition C)

[확실] In the tested OpenSSL and BoringSSL configurations, all 20 `silent-downgrade` records advertised hybrid support, negotiated the classical `X25519` group, completed successfully, had no recorded HRR, and had no automatic downgrade flag. Under the v1.1 design's operational definition, this is a cross-implementation, key-share-order-dependent silent-downgrade observation.

[확실] This result is bounded to the tested group order, versions, configuration, loopback testbed, and audit definition. It does not show that all TLS implementations or deployments have the same behavior, and it does not by itself establish an attacker capability, a CVE, or a new vulnerability.

[불확실] P2/P3 data alone cannot determine whether accepting an offered classical key share in this configuration is prohibited by TLS specifications. The pre-registered design records RFC-conformant behavior as a possibility; a normative RFC analysis and broader security-impact analysis are required before any stronger conclusion.

### On-path stripping control (condition A)

[확실] In the tested TLS runs, the verified `onpath-strip` condition produced 10/10 handshake failures for both OpenSSL and BoringSSL. This is an observation consistent with transcript protection rejecting the tested alteration.

[불확실] These results do not prove a universal fail-closed property for TLS, other versions, other manipulations, or other network environments. They only establish the observed result for the verified manipulations in this dataset.

### Audit visibility (condition B)

[확실] `downgrade_flagged` is false in all 90 final records, including all 20 successful TLS classical-negotiation records in condition C. Under the recorded operational definition, the ordinary captured paths did not automatically surface the advertised-hybrid/negotiated-classical mismatch.

[확실] This does not mean the condition is undetectable: the PCAP and log artifacts contain the fields used for the manual analysis. It means only that the harness did not record an automatic flag through the selected audit paths.

### OpenSSH structural control

[확실] OpenSSH base and `ssh-order` each completed 10/10 hybrid KEX handshakes. Its verified `onpath-strip` runs failed 10/10 while the harness recorded the parsed hybrid KEX name and `is_hybrid=true`.

[확실] The OpenSSH on-path result is a failed connection, not a successful downgrade. SSH does not provide the TLS `key_share`/HRR negotiation structure, so it is a protocol-structure control rather than a third directly comparable TLS data point.

## P3 conclusion and limits

[확실] The supported conclusion is: under the tested group order and audit definition, both TLS implementations completed a classical handshake after hybrid support was advertised, without a recorded HRR and without an automatic downgrade flag. The verified on-path TLS alteration instead failed in the testbed.

[확실] P3 deliberately separates that observation from a security or conformance conclusion. `docs/PAPER.md`, the reproduction package, and the v1.0 historical materials remain unchanged; those updates are deferred to P4 after review of this analysis.

[불확실] Any claim about RFC compliance, practical exploitability, affected deployment population, or vulnerability identity requires evidence beyond this 90-record experiment.
