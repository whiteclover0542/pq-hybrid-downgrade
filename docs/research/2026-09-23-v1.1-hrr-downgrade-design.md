# v1.1 설계 스펙 — HRR 부재에 의한 key_share-의존 하이브리드-PQ silent 다운그레이드 (교차 구현)

- 작성일: 2026-09-23
- 상태: 설계(브레인스토밍 산출), writing-plans 진입 전
- 선행: v1.0 밀스톤(문헌→환경→도구→실행→분석→논문) 완료. 본 스펙은 v1.0 결론의 약점을 교정하는 후속 밀스톤 v1.1.

## 1. 배경과 동기

v1.0의 결론은 두 가지 이유로 약했다.

1. v1.0의 group-list 결함은 **클라이언트가 CLI로 자기 supported_groups를 고전 전용으로 스스로 제한**한 것이라, "고전만 제시하면 고전이 된다"는 동어반복에 가까웠다. 진짜 다운그레이드 *저항성* 시험이 아니었다.
2. CVE-2026-2673의 핵심인 **"감사 도구에 걸리지 않는 조용한 다운그레이드"** 를 시험하지 못했다(v1.0 한계 2에 명시).

## 2. 스파이크로 확정된 사실 (2026-09-23, WSL Ubuntu, 기존 v1.0 빌드)

- [확실] **OpenSSL 3.5.5**: 클라이언트가 `x25519:X25519MLKEM768`로 하이브리드를 **광고**하되 고전 key_share를 먼저 보내고 서버가 하이브리드를 선호(`X25519MLKEM768:x25519`)하면, 서버는 **HRR 없이** 고전을 협상한다(ServerHello 007a=고전, HRR 0, 핸드셰이크 성공). 하이브리드 key_share를 보내면 ServerHello 04ba=하이브리드.
- [확실] **BoringSSL**: 동일 조건에서 동일하게 `ECDHE group: X25519`(고전)로 HRR 없이 협상. 하이브리드 key_share면 `X25519Kyber768Draft00`.
- [확실] **해석(정직)**: 이 거동은 RFC 8446상 서버가 이미 받은 사용 가능한 key_share(고전)를 써서 1-RTT로 끝낼 수 있으므로 **명백한 버그가 아니라 준수 가능 동작일 수 있다**. 따라서 "CVE-2026-2673 버그 재현"으로 규정하지 않는다. 정직한 규정은: **"두 TLS 구현 모두 클라이언트 key_share 선택에 다운그레이드 저항이 좌우되며, 하이브리드를 선호·광고함에도 HRR로 업그레이드를 방어하지 않는다"** 는 교차 구현 속성.
- [확실] **OpenSSH**: SSH KEX는 key_share/HRR 개념이 없는 알고리즘 목록 협상(첫 매치)이라 이 조건 자체가 존재하지 않는다. C의 3번째 데이터 포인트가 아니라 **프로토콜 대조점**이다.

## 3. 연구 질문과 가설 (정직한 프레이밍)

- **가설**: 하이브리드를 선호·광고하는 TLS 1.3 서버가 클라이언트의 고전 key_share에 대해 HRR을 보내지 않고 조용히 고전으로 협상하는 현상은, 특정 라이브러리의 버그가 아니라 독립 TLS 구현에 걸친 공통 속성이다.
- **연구 질문**: 이 key_share-의존 silent 다운그레이드가 (a) 독립 구현 전반의 패턴인가, (b) 표준 감사 도구로 정상 고전 핸드셰이크와 구별 가능한가(=조용한가), (c) 경로상 공격자에 의한 스트리핑에는 TLS 1.3 transcript 방어가 작동하는가.
- **금지**: "CVE-2026-2673 버그를 재현했다", "모든 TLS 라이브러리/실배포에서", "이것이 취약점이다" 류의 확대. RFC 준수 가능성을 결론에 병기한다.

## 4. 실험 설계

### 4.1 변인과 고정
- 변인: 구현(OpenSSL 3.5.5+oqs-provider, BoringSSL, OpenSSH) × 협상 조건.
- 고정: v1.0과 동일한 고정 버전·커밋·빌드(Phase 2 환경 대장), loopback 네트워크, 감사/로깅 경로.

### 4.2 협상 조건
| 조건 | 대상 | 설정 | 관측/기대 |
|---|---|---|---|
| **base** | 3구현 | 클라이언트 하이브리드 key_share, 서버 하이브리드 선호 | 하이브리드 협상, HRR 없음 |
| **C: silent-downgrade** | OpenSSL, BoringSSL | 클라이언트 `고전:하이브리드`(고전 key_share 우선, 하이브리드 광고), 서버 `하이브리드:고전`(하이브리드 선호) | 고전 협상, **HRR 없음**, 성공 → 조용한 다운그레이드 |
| **A: on-path strip** | OpenSSL, BoringSSL, OpenSSH | 클라이언트는 정상 하이브리드 제안, MITM 프록시가 ClientHello/KEXINIT에서 하이브리드 그룹/KEX 제거 | **핸드셰이크 실패**(transcript/exchange-hash 방어) |
| **SSH 대조** | OpenSSH | 클라이언트가 하이브리드+고전 KEX를 순서대로 제안, 서버 선호 | 첫-매치 협상 결과 관측(구조 대조) |

### 4.3 지표 (매 실행, 구조화 원시 데이터)
1. **협상 그룹/KEX**: 하이브리드 vs 고전. 판정 근거 — OpenSSL ServerHello 크기(하이브리드 ~04ba / 고전 ~007a) + 협상 그룹, BoringSSL `ECDHE group`, OpenSSH `kex algorithm`.
2. **HRR 발생 여부**(TLS): ServerHello 개수/HRR 마커. C의 핵심 — HRR 부재가 조용한 다운그레이드의 조건.
3. **핸드셰이크 성공/실패**: A의 fail-closed 판정.
4. **감사 가시성(B)**: pcap의 ClientHello `supported_groups`(하이브리드 광고)와 실제 협상된 고전 그룹의 **불일치가 표준 감사 도구 출력만으로 자동 드러나는가**. 판정 방식 — 각 표준 경로(client log, `-state`/`-vvv`, keylog, pcap 단일 관측)가 "하이브리드가 광고됐으나 미사용" 사실을 표면화하는지 여부를 `downgrade_flagged`(bool)로 기록. 예상: 자동 표면화 안 됨(사람이 광고 vs 협상 diff 필요) = silent.

### 4.4 표본
- 조건×구현 유효 조합당 최소 10회. 조작 실제 적용 검증(`manipulation_verified` 계승; C는 "고전 key_share가 실제 전송됐고 하이브리드가 광고됐는지"를 pcap ClientHello로 검증, A는 "프록시가 실제 제거했는지" 검증).

## 5. 도구 변경 (faultinject 확장 — 재작성 아님)
- `record.py`: 새 지표 필드 추가(`hrr_present: bool|None`, `downgrade_flagged: bool|None`, `advertised_hybrid: bool`), `condition` 축 확장(`base`/`silent-downgrade`/`onpath-strip`/`ssh-order`).
- `harness.py`: ServerHello 크기/HRR 감지 파서, 감사-가시성 판정, 협상 그룹 판정을 세 구현에 맞게 확장.
- `fault_group_list.py` → 조건 빌더로 일반화(또는 `conditions.py` 신설): C 조건은 그룹 순서 설정만(TLS 주입 불필요), SSH 대조는 KexAlgorithms 순서.
- `mitm_proxy.py` + `tls_clienthello.py`/`ssh_kexinit.py`: A 스트리핑 변형(하이브리드 KeyShareEntry/그룹·KEX 알고리즘 제거) 추가. 기존 binding 조작과 공존.
- `verify_applied.py`: C의 "광고+고전 key_share" 검증, A의 "제거 적용" 검증 추가.
- `run.py`/`aggregate.py`/`analyze.py`: 새 조건 축·지표 반영.

## 6. Phase 구성 (v1.1)
- **v1.1-P1 실험 재설계·도구 확장**: 위 도구 변경 + 조건 빌더 + 지표 파서, 합성/기존-로그 단위 테스트.
- **v1.1-P2 재실행**: 조건×구현 유효 조합 ≥10회, 원시 데이터(로그·pcap·JSON) 보존, `manifest` 갱신.
- **v1.1-P3 재분석**: 교차 구현 판정(정직한 프레이밍), divergence·후보 원인·한계, base 대비 대조.
- **v1.1-P4 논문·패키지 갱신**: PAPER.md 결과·논의·한계·초록 갱신, 재현 ZIP 재빌드, AI-공개 갱신, 밀스톤 v1.1 완료.
- Phase 2(빌드 환경)는 재사용, 재빌드 없음.

## 7. 성공 기준
1. 세 구현의 base·조건별 실행이 조합당 ≥10회, HRR 지표 포함해 원시 데이터로 기록된다.
2. C에서 OpenSSL·BoringSSL 모두 HRR 부재 고전 협상이 재현되고, 그 값이 인용된다.
3. B에서 다운그레이드의 감사 가시성(자동 표면화 여부)이 지표로 기록된다.
4. A에서 경로상 스트리핑이 두 TLS 구현에서 fail-closed임이 기록된다.
5. 판정·결론이 "CVE 버그 재현"으로 과장하지 않고, RFC 준수 가능성과 한계를 병기한다.
6. PAPER.md·재현 패키지·공개가 갱신되고 플레이스홀더가 없다.

## 8. 범위 밖 (Out of Scope)
- CVE-2026-2673의 `DEFAULT`/tuple/HRR **소스 코드 수준 결함 자체**의 확정적 재현(준수 동작과의 구분은 소스 분석 필요 — 별도 작업).
- 3개 초과 구현, 실배포/원격 관측.
- full-MITM(인증서 검증 비활성) 강제 다운그레이드(위협 모델 밖).

## 9. 정직성 제약 (전 Phase 적용)
- 모든 판정은 원시 데이터 값 인용. "silent"는 4.3(4)의 조작적 정의로만 사용.
- OpenSSH는 대조점으로만; C의 세 번째 데이터 포인트로 쓰지 않는다.
- RFC 준수 가능성을 결론에 반드시 병기. 관측된 것("HRR 없이 고전 수용")과 해석("버그 대 준수")을 분리.
