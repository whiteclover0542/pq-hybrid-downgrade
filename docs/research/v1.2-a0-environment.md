**질문에 대한 답**: [확실] 있다 — 단, OpenSSL `DEFAULT` 키워드의 tuple 파싱 버그와 동등한 형태는 아니다. BoringSSL은 `SSL_OP_CIPHER_SERVER_PREFERENCE` + 순서가 있는 평평한(flat) 그룹 ID 목록(`SSL_CTX_set1_group_ids`/`SSL_CTX_set1_groups_list`)만 제공하며, OpenSSL의 콜론(`:`)/슬래시(`/`) tuple 구문이나 `DEFAULT` 키워드에 해당하는 구성 문법 자체가 존재하지 않는다. 즉 "그룹 목록을 구조화된 tuple로 해석하다가 실수로 평평한 목록으로 잃어버리는" 버그 클래스가 애초에 발생할 수 없는 API 형태다. `bssl server --help`(위 출력)에도 `-curves`(콜론 구분 목록)만 있고 `SSL_OP_CIPHER_SERVER_PREFERENCE`를 켜는 CLI 옵션은 없다 — 라이브러리 API로만 가능하다.

[확실] 결론: OpenSSL `DEFAULT` CVE와 동등한 설정 수단을 BoringSSL에서 확인하지 못함. 인위적 동등 조건을 만들지 않는다(설계 §4.2). BoringSSL 서버 우선순위 HRR 자체는 존재하지만 이는 표준 RFC 8446 메커니즘이며 CVE-2026-2673이 겨냥하는 "DEFAULT 키워드가 tuple 구조를 잃는" 결함과 다른 범주다.

[확실] v1.1에서 새로 드러난 사실: v1.1 BoringSSL `silent-downgrade`의 ClientHello `key_share`는 `[0x001D, 0x6399]`(X25519, X25519MLKEM768) 두 개였다. 2026-09-28 계획 작성 중 PCAP 원시 바이트를 해석해 확인했으며, Task 2의 `pcap_hello.summarize_hellos()`로 다시 확인할 수 있다. 따라서 v1.1 BoringSSL 행은 "고전 키만 제시"가 아니라, 하이브리드 키도 받은 상태에서 X25519를 선택한 경우로 재해석해야 한다.

## 6. A-0 판정

- 3.5.5 native-only 재사용: **PASS** — §2, providers=`default`만, groups에 `X25519MLKEM768` 존재, `oqsprovider` 없음.
- 3.5.6 수정 대조군 분류: **PASS** — §3, tag `openssl-3.5.6` 존재(`tag-commit=286ddeaac0...`), `HEAD`와 `tag-commit` 일치, `fix-ancestor=yes`, `server version`이 정확히 `OpenSSL 3.5.6`.
- 두 버전 X25519MLKEM768 native 인식: **PASS** — 3.5.5(§2)·3.5.6(§3) 모두 `list -tls-groups`에 `X25519MLKEM768`이 나타나고, oqs-provider 없이 S1/S2 핸드셰이크에서 `Negotiated TLS1.3 group: X25519MLKEM768` 또는 `Peer Temp Key: X25519MLKEM768`(협상 성공)로 협상되었다.
- BoringSSL: **핵심 표본 제외** — §5, `SSL_OP_CIPHER_SERVER_PREFERENCE` + 평평한 그룹 ID 목록만 존재하고 OpenSSL `DEFAULT` 키워드/tuple 구문에 대응하는 설정 수단이 없다(`bssl server --help`에도 CLI 옵션 없음). 설계 §4.2에 따라 인위적 동등 조건을 만들지 않고 "OpenSSL `DEFAULT` CVE 비교에 대한 설정 수단을 확인하지 못함"으로 제한한다.
- **종합: PASS.** 네 항목 모두 통과했으므로 Task 8(다음 실험 단계)로 진행 가능하다. 부가 관측: 3.5.5의 `DEFAULT` 행은 `hrr-random-lines=0`(HRR 생략)으로 CVE-2026-2673과 일치하는 행동을 보였고, 3.5.6의 동일 행은 `hrr-random-lines=1`로 수정되어 있어, 두 버전이 실제로 대조군으로 기능함을 실측으로 확인했다.
