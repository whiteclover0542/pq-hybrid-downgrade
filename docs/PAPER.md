# 하이브리드 PQ 다운그레이드는 구현 간 패턴인가: OpenSSL CVE-2026-2673의 인과 분리 재현과 교차 구현 관측

- 저자: whiteclover0542
- 문서 갱신: 2026-09-29
- 데이터: 정식 실험 270회(교차 구현 관측 90회, CVE 재현 60회, 인과 분리 120회)와 보조 표본 20회

## 초록

TLS 1.3에서 포스트퀀텀(PQ) 하이브리드 키 교환은 클라이언트의 그룹 광고, 초기 `key_share`, 서버의 그룹 선택과 HelloRetryRequest(HRR)가 맞물려 결정된다. 이 협상 로직의 결함으로 하이브리드 협상이 고전 키 교환으로 바뀌는 현상이 특정 라이브러리의 우연한 버그인지, 여러 구현체에 걸친 일반적 패턴인지를 실험으로 검토했다. 기준 사례는 OpenSSL CVE-2026-2673이다. 서버 그룹 설정에 `DEFAULT` 키워드를 쓰면 그룹 우선순위 묶음(tuple) 구조가 사라져 HRR이 생략되는 결함이다. 하나의 고정 클라이언트가 `X25519MLKEM768`과 `X25519`를 광고하되 `X25519` key share만 보내게 하고, 서버 버전과 그룹 설정을 바꿔 가며 각 조합을 10회씩 실행했다. HRR은 패킷 캡처의 RFC 8446 고정 random 값으로 판정했다. OpenSSL 3.5.5 서버는 `DEFAULT` 설정에서 10/10회 HRR 없이 `X25519`로 협상했고, 수정 버전 3.5.6은 10/10회 HRR 뒤 `X25519MLKEM768`으로 협상했다. 명시적 tuple 설정 두 가지에서는 두 버전의 결과가 같았다. 수정 커밋의 라이브러리 변경 한 파일만 3.5.5에 적용하거나 3.5.6에서 되돌리면 `DEFAULT` 설정의 결과가 그대로 뒤집혔고, 3.6 계열(3.6.1/3.6.2)도 같은 방향으로 갈렸다. 따라서 이 결함은 OpenSSL의 설정 해석 경로에서 확인된 결함이다. BoringSSL에는 같은 조건을 표현할 설정 문법이 없고 OpenSSH에는 key share/HRR 구조가 없어, 교차 구현 패턴의 증거는 얻지 못했다. 반면 "하이브리드를 광고했는데 HRR 없이 고전 그룹으로 협상"이라는 겉보기 증상은 두 TLS 구현의 정상 동작에서도 나타났고, 측정한 감사 출력은 어느 경우에도 이를 경고하지 않았다. 증상만으로는 결함과 정상 동작을 구분할 수 없으며, 서버 설정과 버전을 함께 확인해야 한다.

## 1. 서론

하이브리드 키 교환은 고전 알고리즘과 PQ 알고리즘을 함께 써서, 둘 중 하나만 안전해도 세션 키가 보호되게 하는 전환기 방식이다 [2, 3]. 이 보호는 하이브리드 그룹이 실제로 협상될 때만 성립한다. 협상이 조용히 고전 그룹으로 끝나면 연결은 정상적으로 성공하지만 PQ 보호는 사라진다. 지금 트래픽을 저장해 두었다가 양자 컴퓨터로 나중에 해독하는 위협에 대해서는, 그런 연결은 처음부터 하이브리드를 쓰지 않은 연결과 다르지 않다.

2026년 3월 공개된 OpenSSL CVE-2026-2673 [5, 6]은 이런 조용한 전환이 구현 결함으로 일어날 수 있음을 보여 준다. OpenSSL 3.5부터 서버 그룹 목록은 우선순위 묶음(tuple)을 표현할 수 있다. 그런데 설정에 `DEFAULT` 키워드를 넣으면 기본 목록의 tuple 구조가 사라진다. 그 결과 클라이언트가 하이브리드 그룹을 지원하면서도 초기 key share로는 고전 그룹만 보냈을 때, 서버가 HRR로 하이브리드 key share를 요청하지 않고 고전 그룹을 받아들인다. 권고문은 이 결함을 Low 등급으로 분류했고, 3.5.6과 3.6.2에서 수정했다.

본 연구의 질문은 다음과 같다. **협상 로직의 결함이 하이브리드 PQ 다운그레이드로 이어지는 것은 특정 라이브러리의 우연한 버그인가, 여러 구현체에 걸친 일반적 패턴인가?** 이 질문에 답하려면 결함 자체를 재현하고, 결함이 무엇 때문에 생기는지 분리하고, 같은 현상이 다른 구현체에서도 나타나는지 확인해야 한다.

본 연구의 기여는 다음과 같다.

1. 클라이언트를 고정하고 서버 버전과 그룹 설정만 바꾸는 대조 설계로, CVE-2026-2673의 발현과 수정을 한 테스트베드에서 재현했다(§6.1).
2. 수정 커밋의 라이브러리 변경만 넣고 빼는 변형 빌드와 3.6 계열 대조로, 결과 차이가 그 변경 하나에서 온다는 것을 보였다(§6.2).
3. 같은 겉보기 증상이 두 TLS 구현의 정상 동작에서도 나타나고, 측정한 감사 출력이 이를 구분하지 못한다는 것을 관측했다(§6.3, §6.4).
4. RFC 8446은 이 상황에서 HRR을 의무로 두지 않는다. 따라서 결함은 규격 위반이 아니라 구현이 자신이 문서화한 정책을 지키지 못한 것이라고 위치를 정했다(§7.2).

## 2. 배경

### 2.1 TLS 1.3의 그룹 협상과 HRR

TLS 1.3 클라이언트는 ClientHello의 `supported_groups` 확장으로 지원하는 그룹을 광고하고, `key_share` 확장으로 그중 일부의 키 재료를 미리 보낸다 [1]. 서버는 그룹을 독립적으로 고른다. 선택한 그룹의 key share가 이미 와 있으면 ServerHello로 바로 응답하고, 서로 지원하지만 key share가 없는 그룹을 고르면 HRR로 해당 그룹의 key share를 다시 요청한다. RFC 8446은 "호환되는 key share가 없을 때" HRR을 보내도록 요구하지만, 호환되는 key share가 이미 있는데도 더 선호하는 그룹을 위해 HRR을 보내라고 요구하지는 않는다(§7.2).

HRR은 ServerHello와 같은 메시지 형식을 쓰고, 고정된 random 값으로만 구분된다. 따라서 도구의 출력 표기에 의존하면 HRR을 놓칠 수 있다. 예를 들어 OpenSSL의 메시지 추적 출력은 HRR을 `ServerHello`로 표기한다.

### 2.2 하이브리드 그룹

`X25519MLKEM768`은 ML-KEM-768과 X25519를 결합한 하이브리드 그룹이다 [3]. 두 구성 요소의 공개값과 공유 비밀을 연결해 TLS 1.3의 키 스케줄에 넣는다 [2]. 하이브리드 key share는 고전 key share보다 훨씬 크다. 그래서 클라이언트가 초기 key share로 고전 그룹만 보내고, 하이브리드는 서버가 요청할 때 보내는 전략을 쓸 수 있다. 권고문도 이 경우를 결함의 발현 조건으로 든다 [5].

### 2.3 OpenSSL 3.5의 그룹 tuple과 `DEFAULT`

OpenSSL 3.5의 그룹 목록 문법에서 `:`는 같은 tuple 안의 그룹을, `/`는 tuple 경계를 구분한다 [4]. 서버는 선호도가 높은 tuple부터 차례로 살핀다. 현재 tuple 안에 이미 받은 key share가 있으면 ServerHello로 응답하고, 지원 그룹만 있으면 HRR을 보낸다. 내장 기본 목록은 `?*X25519MLKEM768 / ?*X25519:?secp256r1 / ...`처럼 하이브리드 그룹을 별도의 첫 tuple로 둔다. CVE-2026-2673은 설정 문자열 안의 `DEFAULT` 키워드를 이 기본 목록으로 확장하는 과정에서 tuple 경계가 사라지는 결함이다 [5, 7, 8].

## 3. 관련 연구

Bhargavan 등은 설정 가능한 키 교환 프로토콜에서 공격자가 양쪽이 선택했을 모드보다 약한 모드를 강제하는 다운그레이드를 형식화하고, 다운그레이드 저항성의 조건을 분석했다 [9]. FREAK은 TLS 상태 기계의 구현 결함이 [11], Logjam은 수출 등급 Diffie-Hellman 지원이라는 프로토콜 수준의 약점이 [12] 실제 다운그레이드 공격으로 이어진 사례이다. 이들 연구의 초점은 경로상 공격자가 협상을 조작하는 경우이다. 반면 CVE-2026-2673은 공격자 없이 서버의 설정 해석만으로 약한 그룹이 선택되는 경우이며, TLS 1.3의 transcript 보호가 막지 못하는 유형이다. Gupta와 Rana는 하이브리드 PQ 키 설정에서 transcript에 결합된 combiner가 다운그레이드를 막는다는 것을 보였다 [10]. 이 보호는 전송 중 변조를 막지만, 양 끝점이 정상적으로 합의한 고전 협상은 막지 못한다. 본 연구는 이 틈, 즉 규격이 허용하는 범위 안에서 구현의 선택 정책이 PQ 보호의 유무를 결정하는 지점을 다룬다.

## 4. 위협 모델과 범위

공격자는 가정하지 않는다. 결함은 정상 클라이언트와 정상 설정의 서버 사이에서 발현되며, 결과는 하이브리드 대신 고전 그룹으로 협상된 연결이다. 연결의 기밀성과 무결성은 고전 암호 수준에서 유지되지만, 하이브리드가 주려던 PQ 보호는 없다. 영향은 운영자가 하이브리드를 활성화했다고 믿는 동안 일부 연결이 조용히 고전 수준으로 남는 것이다.

범위는 로컬 loopback의 고정 테스트베드이다. 서버는 OpenSSL 3.5.5, 3.5.6, 3.6.1, 3.6.2와 두 가지 변형 빌드이고, 클라이언트는 OpenSSL 3.5.5 하나이다. 교차 구현 관측에는 BoringSSL과 OpenSSH를 포함했다. 실배포 환경의 빈도나 특정 클라이언트 제품의 key share 전략은 다루지 않는다.

## 5. 방법

### 5.1 테스트베드와 고정 클라이언트

모든 TLS 실험은 WSL Ubuntu의 loopback에서 수행했다. 클라이언트는 모든 실행에서 같은 OpenSSL 3.5.5 바이너리, 같은 명령, 같은 환경을 썼다. 클라이언트는 `supported_groups`로 `X25519`와 `X25519MLKEM768`을 광고하고, `key_share`로는 `X25519` 하나만 보낸다. 모든 OpenSSL 빌드는 기본 provider만 사용했다(외부 PQ provider 미사용). 서버는 `-serverpref`를 지정하지 않아 OpenSSL 기본값인 클라이언트 선호 정책으로 동작한다.

### 5.2 서버 그룹 설정

서버 그룹 설정은 세 가지이다. S1 `X25519MLKEM768:X25519`는 두 그룹을 하나의 tuple에 둔다. S2 `X25519MLKEM768/X25519`는 하이브리드를 별도의 첫 tuple로 둔다. S3 `DEFAULT`는 결함 경로이다. 문서화된 선택 규칙 [4]에 따르면, S1에서는 받은 `X25519` key share로 바로 응답하고(HRR 없음), S2에서는 HRR로 하이브리드를 요청해야 한다. S3는 기본 목록의 tuple 구조가 보존되면 S2처럼, 사라지면 S1처럼 동작한다. 보조 조건으로 S4(그룹 설정 생략, 내장 기본 목록 사용)를 따로 실행했고, 이 결과는 판정에 쓰지 않았다.

### 5.3 서버 빌드

CVE 재현(v1.2)에는 영향 버전 3.5.5와 수정 버전 3.5.6을 썼다. 3.5.6 소스는 릴리스 태그를 가리키며, 3.5 수정 커밋 `85977e0` [7]이 그 조상임을 확인했다. 인과 분리(v1.3)에는 네 서버를 추가로 빌드했다. 3.5.5-cherrypick은 3.5.5에 수정 커밋의 `ssl/t1_lib.c` 변경만 적용했다. 이 커밋이 바꾼 라이브러리 코드는 이 파일 하나이고, 나머지는 문서와 테스트이다. 3.5.6-revert는 3.5.6에서 같은 변경만 되돌렸다. 3.6.1과 3.6.2는 3.6 계열의 영향 버전과 수정 버전(수정 커밋 `2157c9d` [8] 포함)이다. 패치 변형은 명령행 실행 파일이 원본과 바이트 단위로 같으므로, 서버마다 `libssl` 해시와 동적 로딩 경로를 기록해 서로 다른 라이브러리를 로드했음을 확인했다(부록 A).

### 5.4 측정과 판정

각 실행은 서버 로그, 클라이언트 로그, 패킷 캡처를 남긴다. HRR은 캡처된 ServerHello의 random이 RFC 8446의 HRR 고정값과 같은지로 판정하고, 클라이언트 로그의 판정은 보조로 대조했다. 최종 그룹은 마지막 실제 ServerHello의 key share 그룹이다. 클라이언트 전제(두 그룹 광고, `X25519` key share 하나)도 캡처로 검증했고, 전제가 깨진 실행은 표본에서 제외한다.

재현 판정 규칙은 실행 전에 정했다. 다음을 모두 만족할 때만 "재현"으로 판정한다. 첫째, S3에서 영향 버전이 HRR 없이 `X25519`로 협상한다. 둘째, 같은 S3에서 수정 버전이 HRR 뒤 `X25519MLKEM768`로 협상한다. 셋째, S1과 S2가 문서화된 대조 결과를 보인다. 넷째, 각 조합이 독립 반복 10회에서 일관되고, 전제·산출물·바이너리 해시가 모두 보존된다. 규칙은 분석 코드로 구현했으며, 캡처와 로그의 HRR 판정 일치와 실제 ServerHello 1개 조건도 함께 요구한다. 인과 분리에는 같은 규칙을 "수정 변경이 있는 서버 / 없는 서버" 기대 행렬로 적용했다.

### 5.5 감사 가시성

"하이브리드를 광고했는데 고전으로 협상됨"이 표준 출력에 드러나는지 출력 경로별로 측정했다. 측정한 경로는 클라이언트 메시지 추적 로그, 서버 로그, 패킷 캡처의 기본 요약이다. 각 경로에 대해 명시적 경고 문구가 있는지, 그리고 하나의 출력 안에서 광고 그룹과 협상 그룹을 함께 식별할 수 있는지를 기록했다. 출력은 있지만 둘 중 하나가 없으면 "판정 불가"로 기록하고, "경고 없음"으로 간주하지 않았다. `s_client -brief` 출력과 key log는 수집하지 않았다.

### 5.6 교차 구현 관측

앞선 실험(v1.1)에서는 OpenSSL, BoringSSL, OpenSSH의 세 구현에서 기본 하이브리드 협상, 고전 그룹 우선 제시, 경로상 하이브리드 제거를 각 10회 관측했다. BoringSSL과 OpenSSH에 대해서는 OpenSSL의 tuple 구문이나 `DEFAULT` 키워드에 해당하는 서버 설정 수단이 있는지도 소스와 도구 옵션에서 조사했다. OpenSSL의 v1.1 서버 설정은 S1과 같은 단일 tuple이었다.

## 6. 결과

### 6.1 CVE-2026-2673 재현

표 1은 60회 실행의 결과이다. 60회 모두 클라이언트 전제가 검증됐고 핸드셰이크에 성공했다.

**표 1.** 서버 버전과 설정별 결과(각 10회)

| 서버 | 설정 | HRR (캡처) | 하이브리드 | 고전 |
|---|---|---:|---:|---:|
| 3.5.5 | S1 단일 tuple | 0 | 0 | 10 |
| 3.5.5 | S2 tuple 경계 | 10 | 10 | 0 |
| 3.5.5 | S3 `DEFAULT` | **0** | 0 | **10** |
| 3.5.6 | S1 단일 tuple | 0 | 0 | 10 |
| 3.5.6 | S2 tuple 경계 | 10 | 10 | 0 |
| 3.5.6 | S3 `DEFAULT` | **10** | **10** | 0 |

두 버전의 결과는 S3에서만 갈렸다. S1과 S2는 두 버전 모두 문서화된 규칙과 일치했다. 클라이언트 로그의 HRR 판정은 캡처 판정과 60회 모두 일치했고, 별도 캡처 분석 도구(tshark)로 표본을 교차 확인한 결과도 같았다. 사전에 정한 네 조건을 모두 만족하므로, 이 고정 테스트베드에서 CVE-2026-2673의 발현 조건과 수정 대조를 재현했다고 판정한다.

보조 조건 S4에서는 3.5.5와 3.5.6 모두 20/20회 HRR 뒤 하이브리드로 협상했다. 같은 3.5.5가 내장 기본 목록을 그대로 쓸 때는 HRR을 보냈다. 따라서 결함은 기본 목록 자체가 아니라 `DEFAULT` 키워드의 확장 경로에서 나타난다.

### 6.2 인과 분리

표 2는 변형 빌드와 3.6 계열의 120회 결과이다. 120회 모두 전제가 검증됐고 핸드셰이크에 성공했으며, 사전에 정한 기대 행렬과 전부 일치했다.

**표 2.** 수정 변경 유무에 따른 S3(`DEFAULT`) 결과(각 10회). S1과 S2는 네 서버 모두 표 1과 같았다.

| 서버 | 수정 변경 | HRR (캡처) | 최종 그룹 |
|---|---|---:|---|
| 3.5.5-cherrypick (3.5.5 + 수정 변경) | 있음 | 10/10 | `X25519MLKEM768` |
| 3.5.6-revert (3.5.6 − 수정 변경) | 없음 | 0/10 | `X25519` |
| 3.6.1 | 없음 | 0/10 | `X25519` |
| 3.6.2 | 있음 | 10/10 | `X25519MLKEM768` |

수정 커밋의 `ssl/t1_lib.c` 변경을 넣으면 영향 버전이 수정 버전처럼, 빼면 수정 버전이 영향 버전처럼 동작했다. S1과 S2는 변하지 않았다. 따라서 표 1의 S3 차이는 3.5.5와 3.5.6 사이의 다른 변경이 아니라 이 변경 하나로 설명된다. 3.6 계열도 같은 방향으로 갈렸다. 다만 3.6 쪽은 릴리스 태그 전체를 비교한 것이므로, 그 차이를 3.6 수정 커밋에 귀속하는 것은 추론이다.

### 6.3 감사 가시성

v1.2의 60회에서 측정한 세 경로 어디에서도 명시적 경고는 없었다(0/60). 광고 그룹과 협상 그룹을 한 출력 안에서 함께 식별하는 것은 60회 모두 불가능했다. 클라이언트 로그는 협상 그룹을 이름으로 보여 주지만 광고 목록은 16진 덤프로만 남고, 캡처의 기본 요약에는 그룹 정보가 없다. v1.1의 90회를 같은 기준으로 다시 계산해도 경고는 0건이었다. 광고와 협상을 한 출력에서 함께 볼 수 있었던 것은 OpenSSH 상세 로그 30건뿐이었다. 결함이 발현된 연결은 측정한 표준 출력에서 정상적인 고전 연결과 구별되지 않았다. `-brief` 출력과 key log에 대해서는 판단하지 않는다.

### 6.4 교차 구현 관측

표 3은 세 구현의 관측 요약이다(각 10회).

**표 3.** 교차 구현 관측(v1.1)

| 구현 | 조건 | 성공 | HRR | 협상 결과 |
|---|---|---:|---:|---|
| OpenSSL | 하이브리드 우선 | 10/10 | 0 | `X25519MLKEM768` |
| OpenSSL | 고전 우선 제시(서버 단일 tuple) | 10/10 | 0 | `X25519` |
| OpenSSL | 경로상 하이브리드 제거 | 0/10 | 10 | 연결 실패 |
| BoringSSL | 하이브리드 우선 | 10/10 | 0 | `X25519Kyber768Draft00` |
| BoringSSL | 고전 우선 제시 | 10/10 | 0 | `X25519` |
| BoringSSL | 경로상 하이브리드 제거 | 0/10 | 0 | 연결 실패 |
| OpenSSH | 하이브리드 KEX / KEX 순서 | 각 10/10 | 해당 없음 | `sntrup761x25519-sha512` |
| OpenSSH | 경로상 하이브리드 KEX 제거 | 0/10 | 해당 없음 | 연결 실패 |

두 TLS 구현 모두 "하이브리드 광고, HRR 없음, 고전 협상"이라는 겉보기 증상을 보였지만, 둘 다 결함이 아니었다. OpenSSL은 S1과 같은 단일 tuple 설정에서 문서화된 규칙대로 동작했다. BoringSSL의 클라이언트는 고전 우선 조건에서도 하이브리드 key share(`X25519Kyber768Draft00`)를 함께 보냈고, 서버는 클라이언트 선호 순서에 따라 `X25519`를 골랐다. 경로상에서 하이브리드 성분을 제거한 경우에는 세 구현 모두 연결이 실패했다. 전송 중 변조는 transcript 보호가 막는다는 뜻이다.

BoringSSL은 순서가 있는 평평한 그룹 목록과 서버 선호 옵션만 제공하며, tuple 구문이나 `DEFAULT` 키워드에 해당하는 설정 문법이 없다. OpenSSH는 알고리즘 목록에서 첫 일치를 고르는 방식이라 key share와 HRR 구조가 없다. 따라서 두 구현에서는 CVE-2026-2673과 동등한 조건을 만들 수 없었다.

## 7. 논의

### 7.1 연구 질문에 대한 답

결함의 원인은 OpenSSL에 있다. 수정 변경 하나로 결과가 켜지고 꺼지며(§6.2), S3에서만 갈리고 기본 목록을 그대로 쓰는 S4에서는 나타나지 않는다(§6.1). 수정 커밋의 제목("Fix group tuple handling in DEFAULT expansion")까지 함께 보면, 결함은 `DEFAULT` 확장 코드 경로에 있다고 보는 것이 타당하다. 이 결함은 한 릴리스의 우연이 아니라 3.5와 3.6 두 계열에 걸쳐 있었다.

교차 구현 패턴의 증거는 얻지 못했다. 다만 이것은 다른 구현이 안전하다는 판정이 아니다. BoringSSL과 OpenSSH에는 같은 버그 클래스가 생길 설정 경로가 없었을 뿐이다. 오히려 두드러진 것은 증상의 보편성이다. 하이브리드를 광고했는데 HRR 없이 고전 그룹으로 협상하는 연결은 결함(OpenSSL `DEFAULT`)에서도, 문서화된 정상 동작(OpenSSL 단일 tuple)에서도, 다른 구현의 선호 정책(BoringSSL)에서도 나타났다. 그리고 측정한 감사 출력은 이들을 구분하지 못했다(§6.3).

따라서 연구 질문에 대한 답은 다음과 같다. **이 다운그레이드를 일으킨 결함은 특정 라이브러리(OpenSSL)의 설정 해석 버그이며, 시험 범위에서 교차 구현 패턴은 관측되지 않았다. 그러나 결함이 만드는 증상은 여러 구현의 정상 동작과 겉으로 같아서, 협상 결과나 표준 로그만으로는 결함 여부를 판단할 수 없다.**

### 7.2 규범적 위치

RFC 8446 §4.1.1은 서버가 그룹을 고르고, "클라이언트가 호환되는 key share를 보내지 않았으면" HRR을 보내야 한다고 규정한다 [1]. 이미 호환되는 key share가 있을 때 더 선호하는 그룹을 위해 HRR을 보내라는 요구는 없고, 그룹 선택 기준도 규정하지 않는다. 따라서 S1과 S3(3.5.5)의 HRR 부재는 그 자체로 규격 위반이 아니다. 차이는 구현 정책에 있다. OpenSSL은 tuple 경계에서 HRR을 보내는 선택 규칙과, 하이브리드를 첫 tuple로 두는 기본 목록을 문서화했다 [4]. S3(3.5.5)는 이 문서화된 정책과 어긋나고, S1은 일치한다. CVE-2026-2673은 규격이 허용하는 범위 안에서 구현이 자신의 설정 정책을 지키지 못한 결함이다. 이 구분은 다른 구현을 평가할 때도 중요하다. HRR 부재만으로 규격 위반이나 결함을 주장할 수 없고, 그 구현이 문서화한 선택 정책과 비교해야 한다.

### 7.3 실무적 함의

운영자에게는 세 가지 함의가 있다. 첫째, 영향 버전(3.5.0–3.5.5, 3.6.0–3.6.1 [5])에서 서버 그룹 설정에 `DEFAULT` 키워드를 쓰면, key share를 미루는 클라이언트와의 연결이 조용히 고전 그룹으로 끝날 수 있다. 수정 버전으로 올리는 것이 근본 해결이다. 둘째, 본 테스트베드에서는 하이브리드를 별도 tuple로 명시한 설정(S2)과 그룹 설정 생략(S4)이 영향 버전에서도 HRR을 발생시켰다. 이는 업그레이드 전 임시 완화책의 후보가 될 수 있지만, 본 연구의 고정 조건 밖에서는 검증하지 않았다. 셋째, 하이브리드 활성화 여부는 설정 파일이나 연결 성공만으로 확인할 수 없다. 실제 협상 그룹을 기록하고 의도한 정책과 비교하는 점검이 필요하다. 본 연구에서 측정한 표준 출력은 그 불일치를 자동으로 경고하지 않았다.

## 8. 한계

실험은 로컬 loopback의 고정 테스트베드에서 수행했다. 서버는 OpenSSL 3.5.5, 3.5.6, 3.6.1, 3.6.2와 두 변형 빌드, 클라이언트는 OpenSSL 3.5.5 하나, 서버 정책은 클라이언트 선호 하나만 시험했다. 다른 버전, 배포판 패키지, 서버 선호 정책, 실배포 네트워크로는 일반화하지 않는다. 각 조합의 반복은 10회이다. 관측된 동작은 결정적이었지만, 반복 수는 안정성 확인 수준이다.

인과 분리는 수정 커밋의 `ssl/t1_lib.c` 변경만 넣고 뺐으며, 같은 커밋의 문서와 테스트 변경은 적용하지 않았다. 3.6 계열은 릴리스 태그 대조만 했고, 3.6 수정 커밋을 단독으로 넣고 빼지는 않았다.

교차 구현 결론은 세 구현과, 그중 동등 조건을 만들 수 있었던 범위에 한정된다. BoringSSL 관측에는 당시의 하이브리드 그룹 `X25519Kyber768Draft00`을 사용했다.

HRR 판정 파서는 여러 TCP 세그먼트에 걸친 핸드셰이크 메시지를 재조립하지 않는다. 본 실험의 메시지는 한 세그먼트 안에 있었지만, 큰 인증서 체인을 쓰는 환경에서는 제약이 될 수 있다. 감사 가시성은 세 출력 경로만 측정했고, `-brief` 출력과 key log는 수집하지 않았다. 실제 클라이언트 제품이 얼마나 자주 하이브리드 key share를 미루는지는 조사하지 않았다.

## 9. 결론

클라이언트를 고정하고 서버 버전과 그룹 설정만 바꾼 대조 실험으로, 이 고정된 테스트베드에서 CVE-2026-2673의 발현 조건과 수정 대조를 재현했다. OpenSSL 3.5.5 서버는 `DEFAULT` 설정에서 HRR 없이 고전 그룹을 받아들였고, 3.5.6은 HRR로 하이브리드를 협상했다. 이 차이는 수정 커밋의 라이브러리 변경 하나로 켜지고 꺼졌으며, 3.6 계열에서도 같은 방향으로 관측됐다. 결함은 OpenSSL의 설정 해석 경로에 있었고, 다른 구현에서는 동등 조건을 만들 수 없어 교차 구현 패턴의 증거를 얻지 못했다. 그러나 같은 겉보기 증상이 여러 구현의 정상 동작에서도 나타나고 표준 출력이 이를 구분하지 못한다. 하이브리드 PQ 보호의 실제 적용 여부를 확인하려면 협상 결과를 서버 설정 정책과 함께 점검해야 한다.

- 바이너리: 클라이언트와 3.5.5 서버의 `openssl` SHA-256 `7b1a89948e5e…`, 3.5.6 서버 `88a896e54ede…`. 패치 변형은 실행 파일이 원본과 같고 `libssl.so.3`이 다르다(3.5.5-cherrypick `ef30c6d8de54…`, 3.5.6-revert `a9d8f36e38b2…`, 3.6.1 `fb70fdbf1a67…`, 3.6.2 `708d5e708526…`; 원본 3.5.5 `a785209382…`, 3.5.6 `aff23fc605…`). 각 서버가 자신의 `libssl`을 로드함을 `ldd`로 확인했고, 실행 파일에는 RPATH/RUNPATH가 없다.
- 소스: 3.5.5 `67b5686b…`, 3.5.6 `286ddeaa…`, 3.6.1 `c9a9e5b1…`, 3.6.2 `fe686e15…`. 변형 빌드는 `tools/v13_build_variants.sh`로 만든다.
- 판정 재계산: `cd tools && python -m faultinject.analyze --v12`는 `CVE-2026-2673 verdict: reproduced`, `--v13`은 `Causal-isolation verdict: consistent`를 출력한다. HRR은 캡처의 RFC 8446 HRR 고정 random `cf21ad74e59a6111be1d8c021e65b891c2a211167abb8c5e079e09e2c8a8339c`로 판정한다.
- 재현 패키지: `dist/`의 ZIP 세 개(v1.1, v1.2, v1.3)는 해당 원시 데이터, 문서, 도구, 테스트를 포함한다.

## 부록 B. 연구 경과

v1.0에서는 클라이언트가 고전 그룹만 제시하는 실험과 PQ 성분 변조 실험을 수행했다. 고전만 제시하면 고전으로 협상되고, 변조는 세 구현 모두에서 실패했다. 이 설계는 결과가 조건에 의해 정해지는 동어반복에 가까워 결함을 시험하지 못했다. v1.1(§6.4)은 하이브리드를 광고한 상태의 key share 순서를 교차 구현으로 관측했다. 처음에는 OpenSSL의 HRR 부재를 결함 후보로 보았으나, 서버 설정이 단일 tuple이라 문서화된 동작임을 확인하고 해석을 정정했다. 이 과정에서 OpenSSL 로그가 HRR을 `ServerHello`로 표기해 한 조건의 HRR이 누락된 것을 캡처로 바로잡았다. 이후 HRR 판정의 기준을 캡처로 바꾸었다. 이 정정이 v1.2의 설정 대조 설계와 v1.3의 인과 분리로 이어졌다.

## 부록 C. AI-대-인간 책임 공개

실험 도구(대조 실행기, 패킷 캡처 파서, 감사 가시성 측정, 판정 코드), 변형 빌드 스크립트, 반복 실행 자동화, 원시 데이터 집계, 규범 분석 초안, 그리고 본 논문 초안의 작성에는 AI가 사용됐다. 각 단계의 산출물은 독립 AI 리뷰어가 원시 데이터와 대조해 검토했다. 저자는 연구 질문, 재현 판정 규칙, 실험 행렬과 인과 분리의 범위와 우선순위를 결정했다. 또한 해석 정정(v1.1의 단일 tuple 해석), 원시 데이터와 해시, 커밋 조상 관계, 결론의 범위를 검토하고 확인했다.
