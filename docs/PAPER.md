# 포스트퀀텀 하이브리드 키 교환의 다운그레이드 저항성: 증명된 설계와 세 구현체의 실제 동작 사이의 간극

- 저자: whiteclover0542
- 문서 갱신: 2026-09-29
- 데이터: 정식 실험 330회(경로상 조작·기준선 60회, 교차 구현 협상 관측 90회, CVE 사례 60회, 인과 분리 120회)와 보조 표본 20회

## 초록

하이브리드 키 교환의 다운그레이드 저항성은 설계 수준에서 형식적으로 분석되어 있다. 그래서 포스트퀀텀(PQ) 전환 중인 조직은 흔히 "표준 하이브리드 구성을 따랐으니 다운그레이드에 안전하다"고 가정한다. 본 연구는 이 가정이 실제 구현에서 성립하는지를 OpenSSL, BoringSSL, OpenSSH 세 구현체로 검증했다. 다운그레이드 경로를 둘로 나누어 시험했다. 하나는 증명이 다루는 **경로상 조작**이고, 다른 하나는 증명이 다루지 않는 **공격자 없는 협상 정책**이다. 첫째, 경로상에서 하이브리드 그룹을 제거하거나 PQ 성분을 변조한 60회는 모두 연결 실패로 끝났고, 다운그레이드는 한 번도 성공하지 않았다. TLS의 그룹 제거는 transcript 결합이, SSH의 PQ 성분 변조는 교환 해시 서명이 막았다. 반면 TLS의 PQ 성분 변조는 결합 검증 이전의 키 형식 검증에서 거부되어, TLS의 컴바이너 결합 자체는 시험되지 않았다. 둘째, 공격자가 없을 때 하이브리드 사용 여부는 선택 정책이 정했다. 클라이언트가 하이브리드와 고전을 함께 광고하되 고전을 1순위로 두면, 서버 그룹 목록에 하이브리드가 먼저 있어도 두 TLS 서버는 기본 정책(클라이언트 선호)대로 HelloRetryRequest(HRR) 없이 고전 그룹을 골랐다. 이는 규격과 각 구현의 문서대로의 동작이다. 반면 OpenSSL에서는 서버가 자신이 문서화한 하이브리드 우선 정책을 지키지 못하는 결함(CVE-2026-2673)이 나타났다. OpenSSL 3.5.5는 `DEFAULT` 설정에서 10/10회 HRR 없이 고전 그룹을 협상했고 수정 버전 3.5.6은 하이브리드를 협상했으며, 수정 커밋의 라이브러리 변경 한 파일을 넣고 빼면 이 결과가 뒤집혔다. 측정한 TLS 기본 감사 출력은 어느 경우에도 경고하지 않았고, 광고 그룹과 협상 그룹을 한 출력에서 함께 보여 주지도 않았다. 결론적으로 결합 계층까지 도달한 경로상 조작은 증명대로 막혔고, 간극은 증명 밖의 선택 정책 영역에 있었다. 관측한 결함은 한 라이브러리의 것이다. 다만 하이브리드 사용 여부가 증명 밖의 선택 정책에 달려 있고 기본 출력으로 드러나지 않는다는 구조는 시험한 두 TLS 구현에 공통이었다.

## 1. 서론

하이브리드 키 교환은 고전 알고리즘과 PQ 알고리즘을 함께 써서, 둘 중 하나만 안전해도 세션 키가 보호되게 하는 전환기 방식이다 [2, 3]. 다운그레이드 저항성, 즉 공격자가 양쪽이 선택했을 방식보다 약한 방식을 강제하지 못한다는 성질은 설계 수준에서 형식화되어 있다 [9]. 하이브리드 결합이 핸드셰이크 transcript에 묶여 있으면 다운그레이드를 막는다는 증명도 프리프린트로 제시되었다 [10]. 이런 결과 때문에 운영자는 표준 하이브리드 구성을 켜면 PQ 보호가 적용된다고 가정하기 쉽다.

그러나 증명은 "하이브리드가 협상된 연결을 공격자가 약하게 바꿀 수 없다"는 것을 보장할 뿐, 애초에 하이브리드가 협상되는지는 보장하지 않는다. 협상 결과는 클라이언트가 무엇을 광고하고 어떤 key share를 먼저 보내는지, 서버가 어떤 정책으로 그룹을 고르는지에 달려 있다. 2026년 3월 공개된 OpenSSL CVE-2026-2673 [5, 6]은 이 선택 과정의 결함만으로, 공격자 없이 하이브리드가 조용히 고전 그룹으로 바뀔 수 있음을 보여 주었다.

본 연구는 이 간극을 세 구현체에서 직접 측정한다. 연구 질문은 다음과 같다.

- **RQ1.** 경로상 공격자가 협상을 조작할 때, 실제 구현은 증명이 보장하는 대로 다운그레이드를 막는가?
- **RQ2.** 공격자가 없을 때, 하이브리드를 지원하는 클라이언트와 서버 사이에서 하이브리드가 조용히 빠질 수 있는가? 그 사실이 표준 감사 출력에 드러나는가?
- **RQ3.** 협상 로직의 결함이 하이브리드 PQ 다운그레이드로 이어지는 것은 특정 라이브러리의 우연한 버그인가, 여러 구현체에 걸친 일반적 패턴인가?

본 연구의 기여는 다음과 같다.

1. 세 구현체 × 결함 유형(고전 전용 제시 기준선, 경로상 그룹 제거, PQ 성분 변조, 고전 우선 광고)의 비교표를 제시하고, 각 거부가 어느 방어 계층(transcript 결합, 교환 해시 서명, 키 형식 검증)에서 일어났는지 구분했다(§6.1, §6.2).
2. 공격자 없는 협상에서 하이브리드 사용 여부가 선택 정책으로 정해지는 것을 두 TLS 구현에서 관측하고, 서버가 자기 정책을 지키지 못한 OpenSSL의 결함을 수정 코드를 넣고 빼는 인과 분리로 확정했다(§6.3).
3. 측정한 TLS 기본 감사 출력이 어느 경우에도 이를 경고하거나 드러내지 않음을 보였다(§6.4).
4. 간극의 위치를 규범적으로 정리했다. 결함은 RFC 위반이 아니라 증명과 규격이 구현의 선택 정책에 맡긴 영역에 있다(§7).

## 2. 배경

### 2.1 TLS 1.3과 SSH의 키 교환 협상

TLS 1.3 클라이언트는 `supported_groups`로 지원 그룹을 광고하고, `key_share`로 그중 일부의 키 재료를 미리 보낸다 [1]. 서버는 그룹을 고른다. 고른 그룹의 key share가 이미 와 있으면 ServerHello로 응답하고, 서로 지원하지만 key share가 없으면 HelloRetryRequest(HRR)로 다시 요청한다. RFC 8446은 호환되는 key share가 없을 때 HRR을 보내도록 요구하지만, 호환되는 key share가 이미 있을 때 더 선호하는 그룹을 위해 HRR을 보내라고 요구하지는 않는다. 핸드셰이크 키는 지금까지의 메시지 전체(transcript)로부터 유도되므로, 전송 중 메시지를 바꾸면 양쪽의 키가 달라져 연결이 실패한다. HRR은 ServerHello와 같은 형식을 쓰고, 고정된 random 값으로만 구분된다.

SSH는 양쪽이 보낸 KEX 알고리즘 목록에서 클라이언트 목록 순서상 처음으로 겹치는 알고리즘을 고른다 [13]. 선택 규칙이 규격에 고정되어 있다는 점이 TLS와 다르다. 서버는 키 교환 결과와 양쪽 협상 메시지를 포함한 교환 해시에 호스트 키로 서명하고, 클라이언트는 그 서명을 검증한다. key share나 HRR에 해당하는 구조는 없다.

### 2.2 하이브리드 그룹

`X25519MLKEM768`은 ML-KEM-768과 X25519를 결합한 TLS 하이브리드 그룹이다 [3]. 두 성분의 공개값과 공유 비밀을 연결해 키 스케줄에 넣는다 [2]. BoringSSL의 시험 빌드는 이전 하이브리드 그룹 `X25519Kyber768Draft00`을, OpenSSH는 `sntrup761x25519-sha512`를 사용한다. 하이브리드 key share는 고전 key share보다 훨씬 크다. 그래서 클라이언트는 초기 key share로 고전 그룹만 보내고, 하이브리드는 서버가 요청할 때 보내는 전략을 쓸 수 있다.

### 2.3 OpenSSL 3.5의 그룹 tuple과 `DEFAULT`

OpenSSL 3.5의 서버 그룹 목록에서 `:`는 같은 우선순위 묶음(tuple) 안의 그룹을, `/`는 tuple 경계를 구분한다 [4]. 서버는 선호도가 높은 tuple부터 살핀다. 현재 tuple 안에 이미 받은 key share가 있으면 ServerHello로, 지원 그룹만 있으면 HRR로 응답한다. 내장 기본 목록은 하이브리드 그룹을 별도의 첫 tuple로 둔다. CVE-2026-2673은 설정 문자열 안의 `DEFAULT` 키워드를 확장할 때 이 tuple 경계가 사라지는 결함이다 [5, 7, 8].

## 3. 관련 연구

Bhargavan 등은 설정 가능한 키 교환 프로토콜의 다운그레이드를 형식화하고, 다운그레이드 저항성의 조건을 분석했다 [9]. Gupta와 Rana는 하이브리드 PQ 키 설정에서 transcript에 결합된 combiner가 다운그레이드를 막는다는 증명을 프리프린트로 제시했다 [10]. FREAK은 TLS 상태 기계의 구현 결함이 [11], Logjam은 수출 등급 Diffie-Hellman 지원이라는 프로토콜 수준의 약점이 [12] 실제 다운그레이드 공격으로 이어진 사례이다. 이들 연구는 경로상 공격자가 협상을 조작하는 경우를 다룬다. 본 연구는 같은 경우를 실제 PQ 하이브리드 구현에서 측정하고(RQ1), 여기에 더해 공격자 없이 선택 정책만으로 하이브리드가 빠지는 경우를 함께 다룬다(RQ2). 후자는 형식 모델이 "양쪽이 선택했을 방식"으로 전제하는 부분 자체가 구현마다 다르게 정해지는 영역이다.

## 4. 위협 모델

두 가지 영역을 구분한다.

- **영역 A: 경로상 조작.** 공격자는 클라이언트와 서버 사이에서 핸드셰이크 메시지를 수정할 수 있지만, 서버의 장기 키는 없다. 성공한 다운그레이드란 양쪽이 하이브리드를 원했는데 연결이 고전 그룹으로 성공하는 것이다. 이 영역은 형식 증명이 다루는 영역이다.
- **영역 B: 공격자 없는 협상.** 공격자는 없고, 정상 클라이언트와 정상 설정의 서버가 협상한다. 결과가 하이브리드 대신 고전 그룹이면, 연결은 고전 암호 수준에서 안전하지만 하이브리드가 주려던 PQ 보호는 없다. 지금 트래픽을 저장해 두었다가 나중에 해독하는 위협에 노출되며, 운영자는 하이브리드가 적용되었다고 믿을 수 있다. 이 영역은 증명의 범위 밖이다.

범위는 로컬 loopback의 고정 테스트베드이다. 실배포 환경의 빈도나 특정 클라이언트 제품의 key share 전략은 다루지 않는다.

## 5. 방법

### 5.1 테스트베드

모든 실험은 WSL Ubuntu의 loopback에서 수행했다. 구현체는 OpenSSL 3.5.5(초기 실험에서는 oqs-provider 0.9.0과 함께, CVE 사례에서는 기본 provider만 사용), BoringSSL, OpenSSH portable의 고정 빌드이다. 각 조합은 10회 반복했다.

### 5.2 결함 유형

표 1의 실험을 수행했다.

**표 1.** 실험 구성

| 코드 | 결함 유형 | 영역 | 방법 |
|---|---|---|---|
| E1 | 고전 전용 제시(기준선) | — | 클라이언트가 고전 그룹/KEX만 제시한다 |
| E2 | PQ 성분 변조 | A | 프록시가 클라이언트 하이브리드 공개값의 PQ 성분(ML-KEM, Kyber, sntrup761 부분)만 비트 반전하고 고전 성분은 그대로 둔다 |
| E3 | 하이브리드 제거 | A | 프록시가 ClientHello의 `supported_groups`·`key_share`(또는 SSH KEXINIT)에서 하이브리드 항목을 지운다 |
| E4 | 하이브리드 광고 + 고전 우선 순서 | B | 클라이언트가 하이브리드와 고전을 광고하되 고전을 1순위로 둔다(OpenSSL은 고전 key share만, BoringSSL은 두 key share를 모두 보냄). 서버 그룹 목록에는 하이브리드를 먼저 나열하되, 서버 선호 강제 옵션은 쓰지 않는다 |
| E5 | 서버 설정 결함 사례 | B | OpenSSL 서버 설정(S1 단일 tuple `X25519MLKEM768:X25519`, S2 tuple 경계 `X25519MLKEM768/X25519`, S3 `DEFAULT`) × 서버 버전(3.5.5 영향, 3.5.6 수정) |
| E6 | 인과 분리 | B | 수정 커밋의 `ssl/t1_lib.c` 변경만 3.5.5에 적용하거나 3.5.6에서 되돌린 서버, 3.6.1/3.6.2로 E5를 반복 |

E1은 조작이 아니라 기준선이다. 클라이언트가 고전만 제시하면 고전으로 협상되는 것은 당연하므로, 이후 결과와 비교하는 기준으로만 쓴다. E5와 E6에서는 하나의 OpenSSL 3.5.5 클라이언트를 고정했다. 이 클라이언트는 `X25519`, `X25519MLKEM768` 순으로 광고하고 `X25519` key share 하나만 보낸다. 따라서 이 사례에서 "다운그레이드"는 클라이언트의 선호가 아니라 서버가 문서화한 정책을 기준으로 한 판정이다. 서버는 `-serverpref`를 지정하지 않아 문서상 기본값인 클라이언트 선호로 동작한다 [4]. 보조 조건으로 서버 그룹 설정을 생략한 S4를 따로 실행했다.

### 5.3 측정

각 실행은 협상된 그룹 또는 KEX, 핸드셰이크 성공·실패와 실패 원인(양쪽 로그의 오류), 패킷 캡처를 남긴다. 조작 실험은 프록시 로그와 캡처로 조작이 실제 적용되었음을 확인했다. HRR은 캡처된 ServerHello의 random이 RFC 8446의 HRR 고정값과 같은지로 판정했다. E5와 E6에서는 클라이언트 전제(두 그룹 광고, `X25519` key share 하나)를 캡처로 검증했다. E5의 재현 판정 규칙은 수집 전에 코드로 고정했다. S3에서 영향 버전은 HRR 없이 `X25519`, 수정 버전은 HRR 뒤 `X25519MLKEM768`로 협상해야 하고, S1과 S2는 문서화된 결과를 보여야 하며, 각 조합은 10회 일관되어야 한다. 로그와 캡처의 HRR 판정 일치, 실제 ServerHello 1개 조건은 수집 뒤 규칙을 강화하며 추가했다(판정 결과는 같음). 감사 가시성은 클라이언트 로그, 서버 로그, 캡처 기본 요약의 세 경로에서, 명시적 경고 문구가 있는지와 한 출력 안에서 광고 그룹과 협상 그룹을 함께 식별할 수 있는지로 측정했다.

### 6.2 영역 A: 경로상 조작

E2와 E3의 60회에서 다운그레이드가 성공한 경우는 없었다. 다만 거부가 일어난 방어 계층은 구현과 조작 방식마다 달랐다.

**E3 하이브리드 제거.** TLS에서는 두 구현 모두 transcript 결합이 막았다. OpenSSL 서버는 하이브리드가 지워진 ClientHello를 받고 HRR로 `X25519` key share를 요청했고, 클라이언트는 이에 응했다. 그러나 양쪽 transcript가 달라 핸드셰이크 키가 어긋났고, 10/10회 `bad record mac`으로 끝났다. BoringSSL은 남아 있던 `X25519` key share로 바로 응답했지만 역시 10/10회 복호화 실패(`BAD_DECRYPT`)로 끝났다. 이것은 하이브리드 협상을 전송 중에 바꾸는 공격을 transcript가 막는다는 증명의 전제와 일치한다. OpenSSH에서는 KEXINIT에서 알고리즘을 지운 뒤 패킷 길이가 블록 정렬을 벗어나, 서버가 10/10회 패킷 형식 오류(`padding error`)로 연결을 끊었다. 이 실패는 조작 방식 때문에 생긴 것이므로, SSH의 협상 방어에 대해서는 판단하지 않는다.

**E2 PQ 성분 변조.** OpenSSH에서는 클라이언트가 10/10회 서버의 교환 해시 서명 검증에 실패했다(`incorrect signature`). 조작된 공개값이 교환 해시에 들어가 양쪽의 해시가 달라진 것으로, 결합에 의한 방어이다. TLS에서는 결합 검증 이전 단계에서 거부되었다. OpenSSL 서버는 10/10회 변조된 값을 유효하지 않은 ML-KEM 공개키로 판정해 거부했고(`illegal_parameter`), BoringSSL 서버도 10/10회 key share 해석 단계에서 거부했다(클라이언트는 `decode_error`). 비트 반전으로 만든 값이 PQ 공개키 형식을 벗어났기 때문이다. 따라서 TLS에 대해서는 "형식이 유효하지만 다른" PQ 공개키로 바꿔치는 경우, 즉 컴바이너 결합 자체가 시험되지 않았다.

정리하면 RQ1에 대해, 시험한 조작 중 성공한 것은 없었고, 결합 계층이 직접 작동한 경우(TLS의 제거, SSH의 변조)는 증명의 예측과 일치했다. 시험 설계가 결합 계층에 도달하지 못한 경우(TLS의 변조, SSH의 제거)는 한계로 남긴다.

### 6.3 영역 B: 공격자 없는 협상과 CVE-2026-2673 사례

**정상 동작(E4).** 클라이언트가 하이브리드를 광고하면서 고전 그룹을 먼저 두면, 두 TLS 구현 모두 10/10회 HRR 없이 `X25519`로 협상했다. OpenSSL 서버 설정은 `X25519MLKEM768:X25519`, 즉 두 그룹을 하나의 tuple에 두는 설정이었다. 이 경우 이미 받은 `X25519` key share로 바로 응답하는 것이 문서화된 동작이다 [4]. BoringSSL 클라이언트는 이 조건에서도 하이브리드 key share를 함께 보냈고, 서버는 클라이언트의 선호 순서에 따라 `X25519`를 골랐다. 두 경우 모두 결함이 아니라 규격과 각 구현의 선택 정책대로의 동작이며, 형식 모델의 "양쪽이 선택했을 방식"과도 어긋나지 않는다. 클라이언트 스스로 고전을 우선했기 때문이다. 다만 서버 그룹 목록에 하이브리드를 먼저 적어 둔 운영자의 의도와는 달리, 서버 선호를 강제하지 않는 한 하이브리드는 쓰이지 않았다.

**결함 사례(E5).** 표 3은 OpenSSL 서버 설정과 버전별 결과이다. 60회 모두 클라이언트 전제가 검증됐고 핸드셰이크에 성공했다.

**표 3.** CVE-2026-2673 사례(각 10회)

| 서버 | S1 단일 tuple | S2 tuple 경계 | S3 `DEFAULT` |
|---|---|---|---|
| 3.5.5 (영향) | HRR 0 · `X25519` | HRR 10 · `X25519MLKEM768` | **HRR 0 · `X25519`** |
| 3.5.6 (수정) | HRR 0 · `X25519` | HRR 10 · `X25519MLKEM768` | **HRR 10 · `X25519MLKEM768`** |

두 버전은 S3에서만 갈렸다. S2의 결과처럼 하이브리드를 첫 tuple로 두는 기본 목록이 보존된다면, S3에서도 HRR로 하이브리드를 요청해야 한다. 3.5.5는 그러지 않았다. 로그와 캡처의 HRR 판정은 60회 모두 일치했고, 별도 캡처 분석 도구(tshark)로 두 표본을 교차 확인한 결과도 같았다. 사전에 정한 판정 조건을 모두 만족하므로, 이 고정된 테스트베드에서 CVE-2026-2673의 발현 조건과 수정 대조를 재현했다고 판정한다. 보조 조건 S4(설정 생략)에서는 두 버전 각각 10/10회 HRR 뒤 하이브리드로 협상했다. 결함은 기본 목록 자체가 아니라 `DEFAULT` 키워드의 확장 경로에서만 나타났다.

**인과 분리(E6).** 표 4는 수정 변경의 유무만 다른 서버들의 S3 결과이다. 120회 모두 전제가 검증됐고 핸드셰이크에 성공했다. S1과 S2는 네 서버 모두 표 3과 같았다.

**표 4.** 수정 변경 유무에 따른 S3 결과(각 10회)

| 서버 | 수정 변경 | HRR | 최종 그룹 |
|---|---|---:|---|
| 3.5.5-cherrypick (3.5.5 + 수정 변경) | 있음 | 10/10 | `X25519MLKEM768` |
| 3.5.6-revert (3.5.6 − 수정 변경) | 없음 | 0/10 | `X25519` |
| 3.6.1 | 없음 | 0/10 | `X25519` |
| 3.6.2 | 있음 | 10/10 | `X25519MLKEM768` |

수정 변경을 넣으면 영향 버전이 수정 버전처럼, 빼면 수정 버전이 영향 버전처럼 동작했다. 따라서 표 3의 S3 차이는 3.5.5와 3.5.6 사이의 다른 변경이 아니라 이 변경 하나로 설명된다. 3.6 계열도 같은 방향으로 갈렸지만, 3.6은 릴리스 태그 전체의 대조이므로 그 차이를 3.6 수정 커밋에 귀속하는 것은 추론이다.

### 6.4 감사 가시성

v1.1 교차 구현 관측 90회(기본 협상, E3, E4; OpenSSH는 E4 대신 기본 조건 반복; 보존 로그로 재계산)와 E5의 60회에서 측정한 세 경로 어디에도 명시적 경고는 없었다. TLS 연결에서는 광고 그룹과 협상 그룹을 한 출력 안에서 함께 식별할 수 없었다. OpenSSL 클라이언트 로그는 협상 그룹을 이름으로 보여 주지만 광고 목록은 16진 덤프로만 남기고, BoringSSL 클라이언트 로그는 광고 목록을 남기지 않으며, 캡처 기본 요약에는 그룹 정보가 없다. 한 출력에서 둘을 함께 볼 수 있었던 것은 OpenSSH 상세 로그(30건)뿐이다. CVE 사례에서 결함이 발현된 연결은, 측정한 기본 출력에서 정상적인 고전 연결과 구별되지 않았다. 결함과 S1의 정상 동작은 전송되는 메시지가 같으므로, 협상 결과만으로 둘을 구분할 수 없는 것은 원리적으로도 예상되는 결과이다.

## 7. 논의

### 7.1 간극은 어디에 있는가(RQ1, RQ2)

증명이 다루는 영역 A에서는, 결합 계층까지 도달한 30회(TLS 그룹 제거 20회, SSH PQ 성분 변조 10회)가 모두 막혔다. TLS의 제거는 TLS 1.3의 일반 transcript 결합이, SSH의 변조는 교환 해시 서명이 막았다. 이 범위에서 구현은 증명의 예측대로 동작했다. 다만 하이브리드 컴바이너 결합 자체(TLS의 PQ 성분 바꿔치기)와 SSH의 KEX 목록 제거 방어는 판정하지 못했다.

간극은 영역 B에 있었다. 하이브리드를 지원하는 클라이언트와 서버가 만나도, 하이브리드가 쓰이는지는 클라이언트의 순서와 서버의 선택 정책이 정했다. 증명은 이 부분을 "양쪽이 선택했을 방식"으로 전제하고 다루지 않는다. 시험한 조건에서 고전 협상이 나온 경우는 모두 클라이언트가 고전을 1순위로 광고한 경우였다. 이때 E4의 결과는 규격대로의 동작이고, CVE 사례만이 서버가 자신의 문서화된 정책을 어긴 경우이다. RFC 8446도 호환되는 key share가 이미 있을 때 HRR로 더 선호하는 그룹을 요청하도록 요구하지 않고, 그룹 선택 기준을 구현에 맡긴다 [1]. 따라서 이 영역에서 하이브리드가 실제로 쓰이는지는 각 구현의 선택 정책과 그 정책을 구현한 코드의 정확성에 달려 있다. CVE-2026-2673은 두 번째 조건이 깨진 경우이다. OpenSSL은 하이브리드를 별도 tuple로 두는 선택 정책을 문서화했지만 [4], `DEFAULT` 경로에서 그 정책을 지키지 못했다. 이것은 RFC 위반이 아니라 구현이 자신의 정책을 지키지 못한 결함이다. 그리고 두 경우 모두 측정한 TLS 기본 출력에서 드러나지 않았다(§6.4).

### 7.2 우연한 버그인가, 일반적 패턴인가(RQ3)

결함 자체는 특정 라이브러리의 것이다. OpenSSL의 결과는 수정 커밋의 라이브러리 변경 하나로 켜지고 꺼졌고(§6.3), 수정 커밋의 제목("Fix group tuple handling in DEFAULT expansion")까지 함께 보면 `DEFAULT` 확장 경로의 결함으로 보는 것이 타당하다. BoringSSL은 tuple 구문이나 `DEFAULT`에 해당하는 설정 문법이 없고, OpenSSH는 key share와 HRR 구조가 없다. 두 구현에서는 동등 조건을 구성할 수 없어 같은 유형의 결함을 시험하지 못했고, 결함 수준에서 교차 구현 패턴의 증거는 얻지 못했다.

그러나 결함이 들어간 틈은 시험한 두 TLS 구현에 공통이었다. 두 구현 모두에서 하이브리드 사용 여부는 증명의 범위 밖에 있는 선택 정책에 달려 있었고, 기본 출력은 광고 그룹과 협상 그룹의 차이를 드러내지 않았다. OpenSSH도 협상이 클라이언트 순서에 달려 있다는 점은 같지만, 선택 규칙이 규격에 고정되어 있고 상세 로그로 광고와 협상을 함께 확인할 수 있었으며, 누락은 관측되지 않았다. 따라서 연구 질문에 대한 답은 다음과 같다. **이번에 관측한 결함은 한 라이브러리의 우연한 버그이다. 그러나 그런 버그가 하이브리드 PQ 보호를 조용히 무력화할 수 있는 구조, 즉 증명 밖에 있는 구현 재량의 선택 정책과 기본 출력의 불가시성은 시험한 TLS 구현들에 공통된 구조이다.** "표준 하이브리드 구성을 따랐으니 안전하다"는 가정은 시험한 경로상 공격에 대해서는 맞았지만, 하이브리드가 실제로 협상되는지는 보장하지 않는다.

### 7.3 실무적 함의

첫째, 하이브리드 활성화 여부는 설정이나 연결 성공만으로 확인할 수 없다. 실제 협상 그룹을 기록하고 의도한 정책과 비교해야 한다. 측정한 기본 출력은 그 불일치를 경고하지 않았다. 둘째, 영향받는 OpenSSL(CVE 레코드 기준 3.5.0–3.5.5, 3.6.0–3.6.1 [6])에서 서버 그룹 설정에 `DEFAULT` 키워드를 쓰면, key share를 미루는 클라이언트와의 연결이 고전 그룹으로 끝날 수 있다. 권고문은 3.5.6과 3.6.2로의 업그레이드를 권하며, 내장 기본 목록을 그대로 쓰거나 tuple을 명시적으로 정의한 설정은 정상 동작한다고 밝힌다 [5]. 본 테스트베드에서도 S2와 S4는 영향 버전에서 HRR을 발생시켰다. 셋째, 서버의 선택 정책이 클라이언트 선호를 따르면, 클라이언트가 고전을 우선하는 한 하이브리드는 쓰이지 않는다. OpenSSL에서 하이브리드를 요구하려면 서버 그룹 목록에서 하이브리드를 별도의 첫 tuple로 명시해야 한다. 다른 구현에서 서버 선호를 강제하는 설정은 시험하지 않았다.

## 8. 한계

실험은 로컬 loopback의 고정 테스트베드에서, 세 구현체의 고정 빌드로 수행했다. CVE 사례의 서버는 OpenSSL 3.5.5, 3.5.6, 두 변형 빌드, 3.6.1, 3.6.2이고, 클라이언트는 OpenSSL 3.5.5 하나이다. 서버 선호 옵션은 켜지 않았다. 다른 버전, 배포판 패키지, 실배포 네트워크로는 일반화하지 않는다. 각 조합의 반복은 10회이며, 관측된 동작은 결정적이었다.

기획 단계의 결함 유형 중 경로상 그룹 순서 조작은 수행하지 않았다(E4의 순서 변경은 클라이언트 설정이다). 경로상 조작에서는 시험 설계가 결합 계층에 도달하지 못한 경우가 있다. TLS의 PQ 성분 변조는 키 형식 검증에서 거부되어 컴바이너 결합 자체를 시험하지 못했고, SSH의 KEX 제거는 패킷 형식 오류로 끝나 협상 방어를 판정하지 못했다. 형식이 유효한 다른 PQ 공개키로 바꿔치는 조작과 패킷 길이를 보정한 KEX 제거가 필요하다. 교차 구현 협상 관측의 OpenSSH `ssh-order` 조건은 기본 조건과 같은 설정으로 실행되어, 사실상 같은 조건의 반복이었다. BoringSSL은 이전 하이브리드 그룹 `X25519Kyber768Draft00`으로 관측했다.

E4와 CVE 사례의 클라이언트는 모두 고전 그룹을 1순위로 광고했다. 하이브리드를 1순위로 광고하고 하이브리드 key share를 보낸 기본 협상에서는 세 구현 모두 하이브리드로 협상했다. 하이브리드를 1순위로 광고하면서 고전 key share만 보내는 조건은 시험하지 않았다. 인과 분리는 수정 커밋의 `ssl/t1_lib.c` 변경만 넣고 뺐으며, 3.6 계열은 태그 대조만 했다.

감사 가시성은 세 가지 기본 출력 경로만 정규식 수준으로 측정했다. 상세 출력 모드(`s_client -trace`, `tshark -V`)나 key log는 측정하지 않았다. HRR 판정 파서는 여러 TCP 세그먼트에 걸친 메시지를 재조립하지 않는다. 실제 클라이언트 제품이 하이브리드 key share를 얼마나 자주 미루는지는 조사하지 않았다. 교차 구현 결론은 세 구현에 한정된다.

## 9. 결론

세 구현체에서 하이브리드 키 교환의 다운그레이드 저항성을 두 영역으로 나누어 측정했다. 증명이 다루는 경로상 조작에서는 결합 계층까지 도달한 조작이 모두 막혀, 구현이 증명의 예측대로 동작했다. TLS의 컴바이너 결합 자체와 SSH의 KEX 목록 제거 방어는 판정하지 못했다. 간극은 증명이 다루지 않는 공격자 없는 협상에 있었다. 두 TLS 구현에서 하이브리드 사용 여부는 클라이언트 순서와 서버 선택 정책이 정했고, OpenSSL에서는 서버가 자기 선택 정책을 지키지 못하는 결함(CVE-2026-2673)이 나타났다. 이 고정된 테스트베드에서 CVE-2026-2673의 발현 조건과 수정 대조를 재현했으며, 그 결과는 수정 커밋의 라이브러리 변경 하나로 켜지고 꺼졌다. 어느 경우에도 측정한 TLS 기본 출력은 경고하지 않았다. 관측한 결함은 한 라이브러리의 것이지만, 하이브리드 PQ 보호가 증명 밖의 선택 정책에 달려 있고 기본 출력으로 드러나지 않는다는 구조는 시험한 두 TLS 구현에 공통이다. PQ 전환에서 "하이브리드를 켰다"와 "하이브리드가 쓰이고 있다"는 별개로 확인해야 한다.

## 부록 B. 연구 경과와 정정

연구는 기획서의 구현체 × 결함 유형 비교로 시작했다(E1, E2). 초기 분석은 E2의 거부를 모두 "바인딩 방어 성공"으로 해석했으나, 실패 원인을 다시 확인한 결과 TLS의 거부는 키 형식 검증에서 일어났음을 알게 되어 §6.2처럼 정정했다. 이후 경로상 제거(E3)와 공격자 없는 협상(E4)을 추가했다(v1.1). 처음에는 E4에서 OpenSSL의 HRR 부재를 결함 후보로 보았으나, 서버 설정이 단일 tuple이라 문서화된 동작임을 확인하고 해석을 정정했다. 또 OpenSSL 로그가 HRR을 `ServerHello`로 표기해 E3의 HRR이 수집 기록에서 누락된 것을 캡처로 바로잡았고, 이후 HRR 판정 기준을 캡처로 바꾸었다. 이 정정들이 E5(서버 설정 대조, v1.2)와 E6(인과 분리, v1.3)으로 이어졌다.
