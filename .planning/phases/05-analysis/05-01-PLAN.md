# Phase 5 결과 분석 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Phase 4의 60건 원시 데이터를 구현체별 비교로 정리하고, 테스트 가능한 가설을 고정한 뒤 "협상 로직 결함발 하이브리드-PQ 다운그레이드가 단일 라이브러리 버그인가 독립 코드베이스 전반의 패턴인가"를 원시 데이터 값만 근거로 판정한다. 가설과 어긋나는 결과를 누락 없이 포함하고, 각 divergence에 후보 원인을 달고, 원시 데이터에 없는 주장은 하지 않으며 한계를 명시한다.

**Architecture:** 재현 가능한 비교표는 원시 JSON에서 스크립트로 생성한다(`tools/faultinject/analyze.py` — 60개 `RunRecord`를 읽어 구현체×결함유형 매트릭스와 협상 그룹·성공/실패·다운그레이드 가시성을 집계). 그 위에 분석 문서(`docs/research/phase-5-analysis.md`)가 (1) 고정 가설·연구 질문·"증명된-안전 대 배포된-안전" 구분, (2) 스크립트가 인용한 값 기반 비교, (3) 두 결함 벡터의 대비 해석과 divergence별 후보 원인, (4) 결론과 한계를 담는다. 판정은 세 독립 코드베이스의 실제 결과에서만 나온다.

**Tech Stack:** Python 3(표준 라이브러리, 기존 `faultinject.record` 재사용), Phase 4 원시 데이터(`docs/research/baselines/raw/phase-4/`, `manifest.csv`). 새 실행·빌드 없음 — 이미 수집된 데이터만 분석한다.

**Spec:** `.planning/REQUIREMENTS.md`의 `REQ-cross-implementation-analysis`·`REQ-hypothesis-lock`, `.planning/ROADMAP.md` Phase 5 성공 기준, `docs/PROPOSAL.md` 2~4장, `docs/research/cve-2026-2673.md`, `.planning/phases/04-execution/04-01-SUMMARY.md`(분석 대상 데이터·기준값).

## Global Constraints

- **원시 데이터 밖 주장 금지**: 모든 판정 문장은 `raw/phase-4/`의 실제 값(협상 그룹, 성공/실패, `downgrade_visible`, `manipulation_verified`)이나 `manifest.csv`를 인용해야 한다. 데이터에 없는 일반화(예: "모든 TLS 라이브러리가", "실배포 환경에서도")는 쓰지 않는다.
- **검증 실행만 판정에 사용**: `manipulation_verified=true` 실행만 결론 표본으로 쓴다. Phase 4에서 6조합 전부 10/10이 검증됐으므로 표본은 조합당 10이다.
- **어긋나는 결과 포함**: 가설과 다른 결과를 숨기지 않는다. 특히 결함 벡터에 따라 결과가 갈리는 점(group-list 대 binding)을 명시하고, 각 divergence에 후보 원인을 최소 1개 단다.
- **증명된-안전 대 배포된-안전 구분**: 하이브리드 컴바이너의 다운그레이드 저항성은 형식적으로 증명된 설계(Bhargavan et al.; "Transcript-Bound Combiners…" 2026-09)라는 점과, 이 연구가 시험하는 것은 그 설계의 배포 구현에서의 as-deployed 거동이라는 점을 분리한다.
- **CVE와의 구분**: CVE-2026-2673은 "감사 도구에 걸리지 않는 조용한" 다운그레이드다. 본 실험의 group-list 결함은 `downgrade_visible=true`(클라이언트 로그에 고전 그룹이 드러남)이므로 "관측 가능한" 다운그레이드다. 이 차이를 결론과 한계에 반드시 적는다.
- **범위**: 3개 구현(OpenSSL 3.5.5+oqs-provider, BoringSSL, OpenSSH)·2개 결함유형·로컬 loopback. 초과 일반화 금지.

## Review Focus

- 모든 판정 문장이 실제 데이터 값을 인용하는가 — "세 구현이 다운그레이드됐다" 같은 문장 옆에 실제 협상 그룹(X25519 / curve25519-sha256)과 조합별 10/10이 붙어 있는지.
- 결론이 데이터를 넘어서지 않는가 — group-list의 "관측 가능한 다운그레이드"를 CVE의 "조용한 다운그레이드"로 확대 해석하지 않는지.
- 두 결함 벡터의 대비가 유지되는가 — group-list(세 구현 다운그레이드) 대 binding(세 구현 거부)을 뭉뚱그리지 않는지.
- divergence마다 후보 원인이 있는가 — 특히 (a) binding이 세 구현에서 거부된 점, (b) group-list 다운그레이드가 CVE와 달리 가시적인 점.
- 비교표가 스크립트로 재현되는가 — 손으로 적은 숫자가 아니라 `analyze.py`가 원시 JSON에서 뽑은 값인지.
- 한계가 정직한가 — CLI 레벨 group-list는 클라이언트 자체 조작이지 진짜 MITM 스트리핑이 아니라는 점, binding 프록시는 실패를 유도하므로 "조용한 수용" 여부는 관측 불가라는 점이 적혀 있는지.

from faultinject.record import Metrics, RunRecord, run_id
from faultinject.analyze import comparison, render_markdown

def _w(d, impl, fault, rep, group, result, verified=True):
    rid = run_id(impl, fault, rep, "default")
    RunRecord(rid, impl, fault, rep, "default",
              Metrics(group, group is not None and "MLKEM" in (group or ""),
                      group is not None and "MLKEM" not in (group or ""), result),
              manipulation_verified=verified, artifacts={}).to_json_path(d)

def test_comparison_groups_and_counts(tmp_path):
    for rep in range(1, 11):
        _w(tmp_path, "openssl", "group-list", rep, "X25519", "success")
        _w(tmp_path, "openssl", "binding", rep, None, "failure")
    c = comparison(tmp_path)
    assert c[("openssl", "group-list")]["success"] == 10
    assert c[("openssl", "group-list")]["downgrade"] == 10
    assert c[("openssl", "group-list")]["groups"] == {"X25519"}
    assert c[("openssl", "binding")]["failure"] == 10
    assert c[("openssl", "binding")]["success"] == 0

def test_render_markdown_is_a_table(tmp_path):
    for rep in range(1, 11):
        _w(tmp_path, "openssl", "group-list", rep, "X25519", "success")
    md = render_markdown(tmp_path)
    assert "| implementation |" in md
    assert "openssl" in md and "X25519" in md

```python
# tools/faultinject/analyze.py
from __future__ import annotations
import sys
from pathlib import Path
from faultinject.record import RunRecord

def comparison(run_dir) -> dict:
    out: dict = {}
    for p in sorted(Path(run_dir).glob("*.json")):
        r = RunRecord.from_json(p)
        c = out.setdefault((r.implementation, r.fault_type),
                           {"n": 0, "verified": 0, "success": 0, "failure": 0,
                            "downgrade": 0, "groups": set()})
        c["n"] += 1
        if r.manipulation_verified:
            c["verified"] += 1
        if r.metrics.handshake_result == "success":
            c["success"] += 1
        else:
            c["failure"] += 1
        if r.metrics.downgrade_visible:
            c["downgrade"] += 1
        if r.metrics.negotiated_group:
            c["groups"].add(r.metrics.negotiated_group)
    return out

def comparison_rows(run_dir) -> list[dict]:
    rows = []
    for (impl, fault), c in sorted(comparison(run_dir).items()):
        rows.append({"implementation": impl, "fault_type": fault, **c,
                     "groups": ",".join(sorted(c["groups"])) or "-"})
    return rows

def render_markdown(run_dir) -> str:
    header = ("| implementation | fault_type | verified/n | success | failure | "
              "downgrade | negotiated group(s) |\n"
              "|---|---|---|---|---|---|---|")
    lines = [header]
    for r in comparison_rows(run_dir):
        lines.append(f"| {r['implementation']} | {r['fault_type']} | "
                     f"{r['verified']}/{r['n']} | {r['success']} | {r['failure']} | "
                     f"{r['downgrade']} | {r['groups']} |")
    return "\n".join(lines)

def main(argv=None) -> int:
    run_dir = Path(__file__).resolve().parents[2] / "docs/research/baselines/raw/phase-4"
    print(render_markdown(run_dir))
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

- [ ] **Step 1: 판정 절을 쓴다 (## 판정)**

  실제 데이터 값을 인용해 벡터별로 판정한다:
  - **group-list 벡터**: 세 구현(OpenSSL·BoringSSL·OpenSSH) 모두 조합당 10/10에서 하이브리드가 고전 전용으로 협상됨 — OpenSSL/BoringSSL `X25519`, OpenSSH `curve25519-sha256`, `handshake=success`, `downgrade_visible=true`. → 협상-목록 조작에 의한 다운그레이드 수용은 **독립 코드베이스 전반의 패턴**이다(단일 라이브러리 버그가 아님).
  - **binding 벡터**: 세 구현 모두 조합당 10/10에서 `handshake=failure`(OpenSSL·BoringSSL은 협상 그룹 기록 전 실패, OpenSSH는 하이브리드 KEX 협상 후 실패), `manipulation_verified=true`. → PQ 성분 위조(결합자 바인딩 위반)는 세 구현 모두에서 거부되며 다운그레이드로 이어지지 않는다.
  - 종합 판정: 가설은 **벡터에 따라 부분적으로 지지된다** — 협상-목록 벡터에서는 패턴, 바인딩-위반 벡터에서는 세 구현 모두 방어. 데이터가 말하는 것 이상으로 "모든 협상 결함이 패턴"이라고 확대하지 않는다.

- [ ] **Step 2: 어긋나는 결과와 후보 원인을 쓴다 (## Divergence와 후보 원인)**

  각 divergence에 후보 원인을 최소 1개:
  - **Divergence A — binding이 세 구현에서 거부됨(가설의 "다운그레이드 패턴" 기대와 다름)**: 후보 원인 — 세 구현 모두 하이브리드 키 교환의 transcript/exchange-hash 바인딩이 PQ 성분 변조를 무결성 검사에서 걸러냄(증명된-안전 설계가 이 벡터에서는 as-deployed로도 유지됨).
  - **Divergence B — group-list 다운그레이드가 CVE-2026-2673과 달리 가시적(`downgrade_visible=true`)**: 후보 원인 — 본 실험의 group-list는 클라이언트가 고전 전용 목록을 스스로 제시하는 CLI 레벨 조작이라 정상적인 고전 협상이 로그에 그대로 남는다. 반면 CVE-2026-2673은 OpenSSL `DEFAULT`/tuple/HRR 내부 경로에서 감사 우회로 발생한 조용한 폴백이다. 즉 본 실험은 "협상 로직이 다운그레이드를 수용하는가"를 시험했고 "다운그레이드가 조용한가"는 시험하지 못했다.
  - **기대/비기대 분리**: 기대(group-list 다운그레이드 재현)와 비기대(가시성 차이, binding 전면 거부)를 표로 분리한다.
